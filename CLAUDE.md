# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Web UI dashboard for a multi-repository workspace manager for Claude Code. Browser interface on `localhost:3741` to view workspace status, TODO progress, reviews, git history, and trigger operations (init, execute, review, create-pr, autonomous, etc.) that run Claude Code via `Bun.spawn` + `claude -p --output-format stream-json`. WebSocket chat server on port 3742 for interactive Claude sessions.

## Commands

```bash
bunx github:sters/ai-workspace-v2 [/path/to/ai-workspace]  # Run via bunx
bun install                                                  # Install dependencies
bun run dev:hot                                              # Development with hot reload
bun run build && bun run start                               # Production build + start
bun run lint                    # Runs both tsc --noEmit AND eslint src/
bun run test                    # Run all tests
bun run test:watch              # Run tests in watch mode
bun --bun vitest run src/__tests__/lib/parsers/todo.test.ts  # Single test file (--bun is required for bun:sqlite)
```

## Configuration

Per-workspace config stored in `{workspaceRoot}/.ai-workspace/config.yml`. Three-tier priority: env vars > config.yml > defaults. Config resolution in `src/lib/config/resolver.ts`, cached on `globalThis`. Workspace root is resolved first (CLI arg > `AIW_WORKSPACE_ROOT` env > cwd), then the config directory is derived from it. Directory layout in `src/lib/config/workspace-dir.ts`.

| Variable | Default | Description |
|----------|---------|-------------|
| `AIW_WORKSPACE_ROOT` | cwd | ai-workspace root (must contain `workspace/` and `repositories/`) |
| `AIW_PORT` | 3741 | Next.js server port |
| `AIW_CHAT_PORT` | 3742 | WebSocket chat server port |
| `AIW_CLAUDE_PATH` | auto-detect | Custom Claude CLI path |
| `AIW_DISABLE_ACCESS_LOG` | `false` | Silence Next.js dev access logs (also `server.disableAccessLog` in config.yml) |

`operations.maxGroupConcurrency` (default 8) caps how many Claude children start at once **within one parallel group**. It is per group, not global, so it multiplies with `maxConcurrent`. Sized to the review fan-out (`2..3 children per repo + 1 cross-repo`, i.e. 7 for two repos); raising it costs concurrency, not tokens, since the same children run either way. Read at call time via `getMaxGroupConcurrency()` (`src/lib/pipeline/constants.ts`), which is the single source for both group runners — see **Parallel group concurrency** in Architecture.

`operations.batchSize` (default 15) is how many **actionable top-level TODO groups** go into one executor call. Only `[ ]` pending and `[~]` in_progress count — `[!]` blocked items are excluded from the split (`batchTodoGroups`, `src/lib/parsers/todo.ts`), so a file's visible item count overstates what gets executed. At `batchSize` or fewer the pipeline takes a **different path**: `batches.length === 1` (`execute.ts`) makes one `buildExecutorPrompt` call over the **whole TODO file**, without the batched prompt's `Focus only on the items listed in the "Current Batch" section` restriction and without the per-batch TODO re-read that lets a batch which ran long resume with fresh context. That re-read is also what makes the loop self-healing: each iteration recomputes the remaining batches, so it exits early when the executor got ahead of the plan. Raising `batchSize` therefore trades those two properties, plus a larger retry blast radius (a failed phase re-runs the entire batch — see **Phase retries**), against the fixed cost of a batch boundary: the tail batch of a measured 10+2 split spent 5 min re-establishing context for two items. 15 was chosen to absorb a typical review follow-up round in one call.

The phase budget is `executePhaseBudgetMs(batchCount, batchSize)` = `batchCount * batchSize * PER_ITEM_BUDGET_MS + 5min` (`src/lib/pipeline/constants.ts`), i.e. per **item of batch capacity** — not per batch. A flat per-batch figure meant raising `batchSize` *shrank* the budget for identical work, since the same items then packed into fewer batches (12 items got 45 min at `batchSize: 10` but 25 min at 20). Budgeting capacity rather than the exact item count deliberately over-allocates on the one-item-over case, and `PER_ITEM_BUDGET_MS` (3 min) is loose against the ~1.85 min/item measured, because overshooting costs nothing while a timeout kill re-runs the whole batch on the same budget (see **Phase retries**).

That helper is the single source for **both** places that budget execute work, which is why it lives in `constants.ts` next to `getMaxGroupConcurrency()` rather than in `execute.ts`: `buildExecutePipeline` calls it with the real batch count, and `autonomous`'s cycle phase calls it via `executeCycleBudgetMs()` with `ROUTINE_BATCH_COUNT` (2), since its phases are built before any TODO file is read. The autonomous one is the budget that actually applies — `runSubPhases` discards the inner pipeline's `timeoutMs` (see Gotchas), so a wrapper tighter than the pipeline it wraps fires first and makes the inner sizing dead code. That is exactly what the two hardcoded copies produced: raising the per-item allowance left `CYCLE_BUDGETS_MS.execute` at 70 min against an inner ask of 95. `CYCLE_BUDGETS_MS` therefore no longer carries an `execute` entry.

The "Open in..." dropdown is configured via the `openers: { name, command }[]` field in `config.yml`. Defaults to one VSCode and one Terminal entry. Legacy `editor`/`terminal` top-level keys are auto-migrated to `openers` at runtime in `normalizeRawConfig` (`src/lib/config/resolver.ts`).

`operations` accepts `model` and `effort` both globally and per operation type, and per step via `operations.<operation-type>.steps.<step-type>.{model,effort}`. `effort` takes any CLI level (`low` / `medium` / `high` / `xhigh` / `max`); `null` falls through to the code-level per-step default (see **Model / effort resolution** in Architecture, which documents the four-rung ladder those defaults form). The generated `config.yml` documents the built-in per-step defaults in a comment block that `migrateConfigContent` keeps in sync — `TYPE_OVERRIDE_HINT_LINES` in `src/lib/config/migration.ts` is the single source of that block for both generation and migration, so update it there when the defaults change.

Other notable `config.yml` sections: `hooks.{sessionStartGitContext,blockDangerousBash}` (auto-managed Claude Code hooks; see Architecture), `suggest.enabled` (default `true`; set `false` to disable the post-operation workspace-suggestion background job triggered from `triggerWorkspaceSuggestion`), `slack.{enabled,botToken,appToken,allowedUserIds,chatModel,chatEffort,chatHeartbeatMs,chatMaxTurnMs,chatProgressModel}` (Slack bot integration; `chatModel`/`chatEffort` tune the conversation feature; `chatHeartbeatMs` (default 60000 = 1 min) / `chatMaxTurnMs` (default 1080000 = 18 min) control interim-progress cadence and the per-turn hard cap; `chatProgressModel` (default `haiku`, `null` disables) is the cheap model that summarizes interim progress to one line; see Architecture).

**Env-var substitution in config.yml** — Any string value can contain `{ENV:VAR_NAME}` placeholders, which are replaced with `process.env.VAR_NAME` at config-load time (`src/lib/config/env-substitution.ts`). Names are uppercase ASCII / digits / underscores. Missing env vars become empty strings with a `console.warn`. This is independent of the hardcoded `AIW_*` env overrides above (which still take precedence over the file). Use it for secrets like Slack tokens.

## Architecture

**Next.js 16 App Router** with React 19, TypeScript strict mode, Tailwind CSS 4, SWR for data fetching. Bun runtime.

### Key architectural patterns

- **SQLite persistence** — Per-workspace database in `{workspaceRoot}/.ai-workspace/db.sqlite` via `bun:sqlite`. DB singleton on `globalThis` (`src/lib/db/connection.ts`). Events are buffered in memory and flushed every 5000ms or 50 events (`src/lib/db/event-buffer.ts`).
- **Pipeline orchestration** — Operations are sequences of `PipelinePhase`s (single child, parallel group, or TypeScript function). Entry point: `startOperationPipeline()` in `src/lib/pipeline/orchestrator.ts`. Max 3 concurrent operations. Pipeline definitions per operation type in `src/lib/pipelines/`. Operations interrupted by a server shutdown are NOT resumed — on restart `failStaleOperations()` (`src/lib/pipeline/cleanup-stale.ts`) settles each stale "running" row as failed (or completed if all phases finished), since resuming re-runs side effects and revived operations that didn't need it. Function phases can dynamically add phases via `appendPhases()` — the execution loop re-evaluates `phases.length` each iteration. The `runSubPhases()` utility in `src/lib/pipelines/actions/run-sub-phases.ts` runs sub-pipeline phases within a function phase context, handling all three phase kinds uniformly.
- **Claude CLI execution** — `src/lib/claude/cli.ts` spawns `claude -p --output-format stream-json`. Handles `AskUserQuestion` via `--resume {session_id}`. Re-exported from `src/lib/claude/index.ts`.
- **SSE streaming** — Clients connect to `/api/events?operationId=` for real-time operation output. Replays existing events on connection.
- **Instrumentation split** — `src/instrumentation.ts` delegates to `src/instrumentation-node.ts` at runtime to avoid bundling Node.js-only imports (SQLite, stale-operation cleanup) into Edge Runtime.
- **Two-server setup** — `bin/start.ts` spawns Next.js (`bin/next-server.ts`) and the WebSocket chat (`bin/chat-server.ts`) as separate processes; the Slack bot (`bin/slack-server.ts`) is spawned as an optional third process when `slack.enabled` + tokens are present.
- **The browser terminal owns the chat PTY's size** — the interactive chat's viewport is an xterm instance in a flex layout, so the PTY is spawned at the size that terminal reports (`cols`/`rows` on the `start` message) and told about every later change (`resize` → `terminal.resize()`, which raises SIGWINCH and makes the TUI repaint). Previously the PTY was fixed at `DEFAULT_PTY_COLS`×`DEFAULT_PTY_ROWS` (120×40) and the `resize` message was an explicit no-op, so Claude drew boxes and status lines at a width the viewport did not have and the frame garbled — interleaved characters, a duplicated status line. Three details are load-bearing. `useTerminal`'s `init()` **awaits** the fit rather than deferring it to a `requestAnimationFrame` callback, because callers read `term.cols` immediately after awaiting it (chat's `start`/`resume` payload, the claude-usage request) and a deferred fit hands them xterm's construction default. Refit is driven by a **`ResizeObserver` on the container**, not just `window.resize`: the sidebar and tab chrome move the terminal's width without the window changing size. And a resumed session is resized **after** `replay_done` and only when the size differs — the replayed bytes were drawn at the old size, so the repaint has to land after them, while an identical size needs no repaint at all. Sizes are clamped (`clampPtySize`, `src/lib/pty.ts`), since a terminal measured mid-transition reports 0.
- **A chat session's opening message is pointers, not a corpus** — the init prompt (`templates/prompts/chat.ts`) names the workspace path and the files to open; the session's own first turn is `cd` → one `Read` of `README.md` (plus the review/research `SUMMARY.md` for those two variants) → one short acknowledgement. The TODO files and remaining artifacts are named as available and left unread.

  It used to inline them: the README body, a computed cross-file TODO progress table, and the review summary all went into the positional prompt so startup cost no tool calls. That bought a snapshot of exactly the files an operation rewrites while the conversation is open, and — since the positional argument *is* the visible first message in an interactive PTY — dumped the whole README into the browser terminal. The embedding also had to be defended in prose: the model read the pre-loaded content as a work list and started running git/gh/Read before the user said anything, which is why the system prompt still carries `silent reference` and `only once the user asks`.

  The startup-latency argument that motivated embedding does not transfer to the read, because the cost it measured was not the read. The pre-embedding prompt said *"read the workspace README.md … **then let me know what you find**"* — the report-back is what fanned out into README → TODO → git log. A bounded `Read` with a one-sentence reply gives that no opening; the exchange is one extra tool call.

  **The README is a start-up precondition, not a fallback.** `handleStart` refuses the session with an `error` frame when `README.md` is absent, and refuses **before** killing the caller's existing session — a rejected start must not cost them a live one. Rendering a `(no README.md)` placeholder instead put the model in the one state that reliably provokes the sprawl above: hunting with `ls`/`Glob` for a file the prompt promised. A caller-supplied `initialPrompt` opts out of both the gate and the built prompt.
- **Zod validation** — `src/lib/schemas.ts` for HTTP request bodies, `src/lib/runtime-schemas.ts` for untrusted runtime data (JSONL, WebSocket messages, SSE events, CLI stream fragments). Intentionally separate files.
- **Best-of-N pattern** — Operations like review, execute, create-pr, update-todo support parallel "candidate" runs. `buildBestOfNPipeline()` in `src/lib/pipelines/best-of-n.ts` runs N candidates, then a synthesizer phase reviews all results. Controlled by `bestOfN` in config (per-operation-type overrides supported).
- **Batch & autonomous chaining** — Batch pipelines chain operation types (init → execute → review → create-pr) with configurable gating. Autonomous mode loops execute → review → create-pr up to `maxLoops` times with autonomous gate logic. Both use `startWith` to indicate the first phase.
- **README clarity gate** — a fresh autonomous `init` run (not resume) inserts an `Analyze README clarity` function phase (`buildReadmeClarityGatePhase` in `src/lib/pipelines/autonomous.ts`) right after the README is drafted and BEFORE any execution. Cycle 1 is not queued upfront; the gate runs an AI judge (`readme-clarity-gate.ts` prompt, `README_CLARITY_GATE` step, opus/low) — alongside the criteria-feasibility judge in the same `runChildGroup`, see below — and `appendPhases([Execute, Review, Gate])` only when the drafted README is a clear, grounded "done" contract. Its `timeoutMs` covers the slower of the two judges, not their sum. The phase keeps the label `README_CLARITY_PHASE_LABEL` because the Slack notifier locates the stop message by phase label. If it's too vague/fabricated to implement autonomously, the run stops gracefully (returns `true`, appends nothing) and `emitResult` recommends refining the README via update-readme — no code is touched. Fails open (proceeds) on any judge error/parse failure. It is a safety valve, not a quality bar (biased toward proceeding).
- **Criteria feasibility gate** — the judge runs where the `(auto)` criteria are **written**, not on every run that reads them. `prepareCriteriaFeasibility()` (`pipelines/actions/criteria-feasibility.ts`) returns it as a `GroupChild` plus an `apply()` that writes its verdict, so it runs two ways: on the autonomous **init** path as a **second child of the clarity gate's `runChildGroup`** — both judges only read the drafted README, ask independent questions of it, and used to be serialized for no reason but wall clock — and as the trailing `Check criteria feasibility` phase of **update-readme** (`buildCriteriaFeasibilityPhase`, via `runChild`), the operation that invalidates an earlier verdict by rewriting the contract. It sits last there because it reads every worktree the README declares, so repository setup must have run; it is deliberately **not** excluded from the `interject` path, since an interject re-kicks autonomous and that re-kick does not judge. An autonomous run starting from `execute` / `update-todo` no longer judges at all: it re-reads a contract already judged where it was written, and paid a serial worktree-reading phase (~3 min, ~$1.9) per run for a verdict already sitting in the ledger — a PR-review turnaround paid it before touching any code. The cost of the gap is a workspace whose README was never judged (`init --only` from Slack, or a hand-edited README) reaching a cycle with an unreachable criterion. It returns `null` when the README has no `(auto)` criteria, which is the caller's cue to skip the child entirely. When the clarity gate stops the run, the feasibility verdict is **discarded rather than applied**: it judged criteria that update-readme is about to rewrite. The clarity gate asks whether the contract is *clear*; this asks whether each `(auto)` criterion is *achievable inside these repositories* (`criteria-feasibility.ts` prompt, `CRITERIA_FEASIBILITY` step, opus/medium, reads every worktree). A criterion can be clear, grounded, and still impossible — the usual shape being cross-repo, where satisfying it needs a schema change another team owns. Nothing else detects that: the README verifier reports it UNSATISFIED every cycle, the reviewers re-derive why every cycle, and the gate keeps looping toward a target no cycle can reach. Infeasible criteria are written to the **known-findings ledger** as `infeasible`; the run then **continues** on the rest of the contract (unlike the clarity gate, this never stops it). Fails open in both directions — a judge error or parse failure proceeds with all criteria, and the prompt is biased toward "feasible" because a wrong "infeasible" silently deletes real work behind an authoritative-looking justification. Skips the judge entirely when the README has no `(auto)` criteria.
- **Known-findings ledger** — `artifacts/known-findings.md` per workspace (`src/lib/workspace/known-findings.ts`), the pipeline's only cross-cycle memory of findings it decided *not* to act on. Review agents are spawned fresh each cycle and the gate only receives its own past `reason`/`fixableIssues` strings, so without it an unactionable finding is re-derived and re-reported at full length forever — an unsatisfiable criterion, another team's escalation, a pre-existing tooling failure. Writers: the autonomous gate (`dismissedFindings` in `AUTONOMOUS_GATE_SCHEMA`, tagged with the cycle number) and the feasibility gate. Readers: `review.ts` passes the raw content to the code reviewer and cross-repo reviewer (`knownFindings`), and `runAutonomousGate` passes it back to the gate. Entries are `- **[kind]** (cycle N) summary` + a `Why not acted on:` sub-bullet; `kind` ∈ `out-of-scope` / `pending-human` / `infeasible` / `pre-existing` / `low-confidence` / `deferred`, with unknown kinds coerced to `deferred` (the weakest claim — guessing a stronger one would assert the finding is permanently dead). Dedup is on the summary reduced to lowercase alphanumerics, since two cycles rarely word a recurring finding identically. `RECURRING_FINDINGS_POLICY` (`shared.ts`) is the reviewer half of the contract: a listed finding still gets **reported** (coverage is untouched) but compressed to one `(Recurring)` line outside the severity counts, unless it merely *resembles* a listed one or has *materially changed*. The gate half: a listed finding never justifies `shouldLoop: true`, and a review containing only recurring findings means proceed. The collector keeps the recurring bucket out of `SUMMARY.md`'s counts and Top Priority list.
- **Suggestion budget** — the run's deliverable is a **review-ready branch**: the README contract implemented, correct and complete. The cycles exist to reach that, so the loop bar is the deliverable's own state, not a prediction of what a later human reviewer will say — that framing turns every plausible opinion into a cycle. One bar, the same on **every** cycle: `shouldLoop: true` requires a Critical/Must-Fix/Should-Fix finding, an unmet actionable `(auto)` criterion, a pending in-scope TODO item, or a requested fix the verifier found unlanded. Suggestion-level findings never clear it; they are recorded as `deferred` in `dismissedFindings`. The reason is mechanical rather than aesthetic: each suggestion fix widens the diff, the next review reads the wider diff and therefore finds more — including findings about the fix itself — so a polish cycle costs a full Execute + Review and spends it while real incompleteness waits.

  This used to start at cycle 2, with the gate's `Default to fixing` / "don't skip Suggestions" rules applying in full on cycle 1. Those rules predate the review harness that feeds them: once `REVIEW_COVERAGE_POLICY` stopped the reviewers self-filtering, *every* cycle 1 had an actionable nit in it, so no run could finish in one cycle and a one-line task cost three. Nothing is restated per cycle in the user prompt any more, because the rule no longer depends on the cycle number.

  What makes a severity-based bar safe is that the severity label means something, which is `SEVERITY_CALIBRATION`'s job (see **Prompt conventions**): the gate's prompt additionally forbids reading the budget as licence to down-label, and names insufficient test coverage as Should-Fix rather than a Suggestion — but **scoped**, not absolute. Missing coverage clears the bar only for behavior the README's contract requires or that a reachable input exercises; an untested **defensive guard** no reachable input hits is a Suggestion. Absolute is a bar with no fixed point, because every fix a cycle lands is itself changed code carrying new guards, so the run's own fix supplies the next cycle's blocker and no branch state ever clears it. That is not hypothetical: on the run this was written for, cycle 1 fixed a real NaN comparator, cycle 2 then looped on the single ask of testing the NaN-fallback guard *that fix had introduced*, and cycle 3 spent an Execute + Review on 18 lines of test — the feature work had been finished in cycle 1.

- **A PR means the branch is review-ready** — `create-pr` is appended only when the gate clears the **Completion Bar**: no unresolved Critical/Must-Fix/Should-Fix finding, every actionable `(auto)` criterion satisfied, every earlier ask `LANDED` or retired on the record, and no in-scope `[ ]` / `[~]` TODO item left. (A `[!]` blocked item does not hold the PR — it waits on a human, not on another cycle, so it is recorded as `pending-human`. Deferred Suggestions and `(manual)` criteria likewise don't.)

  Reaching `maxLoops` (API default **3**, `operations/autonomous/route.ts`) with work still outstanding therefore **stops the run without a PR**: the gate phase emits `FINAL_CYCLE_STOP_PREFIX` (`autonomous-gate.ts`) with the remaining items and the update-todo → autonomous handoff, and the Slack notifier relays that via `extractIncompleteStop` instead of the misleading "no PRs were created" — the same relay the README clarity gate gets, for the same reason. Previously the last cycle short-circuited (`loopIteration >= maxLoops` returned before the model call) and opened a PR "regardless of issues found", which both discarded that cycle's entire review — the most expensive phase of a cycle, and nothing downstream reads it, since `create-pr` takes only the README and the diff — and handed a human a PR containing the run's own leftover TODO items. The gate now evaluates the final cycle like any other; `shouldLoop` is read as *work remains* and the pipeline decides whether that means another cycle or a stop.

- **Every cycle has one shape** — when the gate loops, the pipeline always appends `Cycle N: Update TODO` → `Cycle N+1: Execute` → `Cycle N+1: Review` → `Cycle N+1: Gate`. There is no second shape and nothing for the gate to choose: `fixableIssues` becomes the instruction for `Update TODO`, an executor works from the resulting plan, and the diff that produces is reviewed by the full child set — code reviewer, `verify-fixes`, `verify-todo`, `verify-readme`, cross-repo, `Verify constraints`, collect. A fix round is narrowed by the **incremental review baseline** (the diff since the last review), never by dropping reviewers.

  It briefly had a second shape. A `fixScope: "targeted"` verdict skipped the plan and handed the numbered asks straight to a `fix-applier` child, behind a `scope: "fixes"` review that ran only `verify-fixes` + `verify-readme` + constraints + collect. The motivating measurement was real — one cycle spent 14.8 min (`Update TODO` 2.6, `Execute` 5.3, `Review` 6.0, `Gate` 0.9) to land a one-line `key={item.id}` fix and one hook spec — and the 2.6 min of re-planning genuinely buys little when the ask already names the site and the change.

  **What it traded was the code review of the fix diff**, and that is why it is gone. It was built as an opt-in exception for asks whose whole shape the gate could already see, with "when in doubt, choose `replan`" in the prompt. Measured over the five autonomous runs that reached a cycle-1 gate after it shipped, the gate chose `targeted` on **4 of 4 loops** and `replan` on none — so the exception was the rule, and the newest, least-examined code on the branch was the one part nothing hunted for defects in before the PR. The saving was ~2.6 min against a cycle; the cost was an unreviewed diff reaching a human. Historical data says the same shortcut was never load-bearing: of 12 sampled pre-`targeted` cycle-1 loops, 11 looped on "a concrete Warning with a fix attached at a named site" — i.e. the case `targeted` was for — and the full round handled all of them.

  The accepted cost of uniformity is the diff-widening risk the **Suggestion budget** exists to contain: a full review of a fix diff can find new findings *in the fix*, which is another loop. What holds that down is the severity contract rather than a reduced review — `SEVERITY_CALIBRATION`'s untested-path rungs, the Suggestion budget's one bar, `RECURRING_FINDINGS_POLICY`, and the small diff the incremental baseline hands the reviewer. `maxLoops` bounds the rest, so the failure mode is a `FINAL_CYCLE_STOP_PREFIX` stop rather than an unbounded run.
- **Phase update markers** — Phase lifecycle is communicated via special JSON prefixes in status events: `"__phaseUpdate:"` and `"__setWorkspace:"`. These are parsed by `parsePhaseUpdatesFromEvents()` / `parsePhaseUpdatesFromEntries()` to rebuild phase arrays from the event stream without needing a separate phases table.
- **Function phase context** — TypeScript function phases receive a `PhaseFunctionContext` with `emitStatus()`, `emitResult()`, `emitAsk()` (blocks until user answers), `runChild()` / `runChildGroup()` (spawn Claude sub-processes), `emitTerminal()` (raw PTY output), `appendPhases()` (dynamic phase injection), `setWorkspace()`, and `signal` (AbortSignal for kills). Child processes accept `allowedTools` (explicit tool restrictions — overrides auto-generated patterns from `addDirs`), `appendSystemPromptFile` (appended to Claude's system prompt), `stepType` (for config-based model resolution), and `skipAskUserQuestion`.
- **Model / effort resolution** — `resolveModel()` and `resolveEffort()` in `src/lib/config/model.ts` share one 6-tier priority chain: explicit (phase/child) > per-operation per-step config > per-operation config > global `operations.model` / `operations.effort` > code-level `STEP_DEFAULT_MODELS` / `STEP_DEFAULT_EFFORTS` > CLI default. Both are wired through `phase-runners.ts` / `context-builder.ts` for single phases, group children, `runChild`, and `runChildGroup` (plus `suggest-workspace.ts`, which spawns outside the pipeline). **Effort, not the model tier, is the primary cost/latency dial** — hence effort is declared explicitly for every step that declares a model rather than inherited from the CLI. The two tables must cover exactly the same step types; `effort.test.ts` fails on drift.

  The two tables are **two halves of one ordered ladder with exactly four rungs**, cheapest first. `effort.test.ts` fails on a fifth pairing, so a new step type must land on a rung rather than invent one.

  | rung | meaning | steps |
  |---|---|---|
  | sonnet / low | purely mechanical — nothing to decide | `prune-suggestions`, `collect-reviews`, `verify-todo`, `deep-search`, `aggregate-suggestions` |
  | opus / low | a step above mechanical — shallow judgment over a bounded input | `discover-constraints`, `create-pr`, `readme-clarity-gate`, `best-of-n-file-reviewer`, `best-of-n-synthesizer` |
  | opus / medium | **the default rung** | `execute`, `code-review`, `verify-readme`, `criteria-feasibility`, `validate-pr-comment`, `ground-finding`, `resolve-conflicts`, `update-readme`, `plan-todo-from-review`, `review-todos`, `suggest-workspace` |
  | opus / high | needs real thought — open-ended, no checklist | `analyze-readme`, `plan-todo`, `research`, `coordinate-todos`, `best-of-n-reviewer`, `autonomous-gate`, `update-todo` |

  Sonnet appears on the bottom rung **only**, which is the whole reason to reach for the smaller model: cheap throughput on work with nothing to decide. Sonnet at `medium` or `high` is a rung this ladder deliberately does not have — paying more to make the weaker model think is the wrong trade, so anything above mechanical goes to opus and the dial becomes effort alone. `model.test.ts` enforces that sonnet implies `low`. There is likewise **no haiku tier**: a current-generation Sonnet at low effort beats a smaller model at high effort for comparable spend, and these steps feed the autonomous gate where a silent misread is expensive. `xhigh` / `max` are never code-level defaults: reach for them per-workload via config, measured.

  A step's *importance* is explicitly **not** what moves it up. Nearly every step feeds something downstream that treats its output as authoritative, so "the pipeline enforces this as fact" argues for `high` everywhere and therefore discriminates nothing — that reasoning is what once put 9 of 24 steps at high. What earns the top rung is the **absence of a checklist**: `coordinate-todos` reads the *other* repos' source to resolve `[CROSS-REPO]` placeholders into concrete names, `analyze-readme` / `plan-todo` decide what "done" means and how to reach it, `best-of-n-reviewer` judges and merges implementations it didn't write. `verify-readme` is the instructive contrast: it gates the whole run, but it checks the enumerated `## Acceptance Criteria` list, so it is bounded and sits on the default rung — as does `criteria-feasibility`, which asks a different bounded question about the same enumerated list (see **Criteria feasibility gate**) and sits a rung above `readme-clarity-gate` only because answering it means reading the other repositories' source. `autonomous-gate` is the one step placed by payoff rather than shape — it reads an already-structured summary, but it's a single short call whose wrong answer costs a whole cycle in either direction.

  `code-review` is the ladder's **one placement made by budget rather than by shape**, and it is flagged as an exception rather than reasoned into the rung. By the absence-of-a-checklist rule it belongs at `high` — hunting defects nobody enumerated is the definition of open-ended — and that is where it sat. It moved because it is the measured critical path of *every* review phase (7.4 min / 40 turns on cycle 1 of one autonomous run, 4.9 on cycle 2, with under 10s of either spent waiting on a tool), and a review phase runs once per cycle. What makes the trade survivable is how much of the reviewer's job the harness around it now owns: `REVIEW_COVERAGE_POLICY` asks it for breadth rather than adjudication, `SEVERITY_CALIBRATION` supplies the labels, `Verify constraints` owns lint/test/build, and **Incremental review scope** narrows it to the diff since the last review. Review depth is genuinely what got traded; `operations.review.steps.code-review.effort` puts it back per workload.

  `update-todo` is the top rung's least obvious member, because it reads like translation — the gate's numbered asks become TODO items — and it sat on the default rung for exactly that reason. What it actually has to derive is enumerated nowhere: which sites *state* a contract an ask changes, and which of the sites its own items touch need test coverage. On the run that moved it, one cycle's items named four doc sites and missed the interface declaration — the only file with no code change of its own — and changed five error-return sites while commissioning tests for two; all three gaps returned as the next review's Warnings, so each cost the same cycle a wrong gate answer costs. It is also the cheapest agentic phase in a cycle (~3 min of an 84-min run, against 12–22 min for the Execute it feeds), which makes it the cheapest place in the pipeline to buy judgment. `plan-todo-from-review` does the same shape of work and deliberately stays at medium: it is a standalone operation whose TODO a human reads before anything executes, where this one hands straight to an executor in the same run with nothing in between. The prompt rules the same run produced are in `### Deriving an Item's Targets` (see **`SCOPE_DISCIPLINE`** in Prompt conventions) — effort was raised alongside them, not instead of them, since a higher rung applied to a wrong derivation rule just applies it more thoroughly.

  `execute` sits at medium despite being the most consequential step: the planning steps ahead of it already decided what to build and the review/gate phases behind it verify the result, so it is bounded implementation against a TODO. It is also the longest-running step and runs once per batch per repo, so it dominates both wall clock and spend. Note that `~/.claude/settings.json` `effortLevel` is what the CLI default resolves to, so before `STEP_DEFAULT_EFFORTS` existed every step inherited *that* — don't read a step's arrival at `high` as a change from an unset baseline.

  Two placements are non-obvious. `research` is one step type covering all three research phases (per-repo + cross-repo findings, recommendations, integration), tiered for the findings phases since they are the operation's deliverable rather than a step toward one. The best-of-N steps are split by *what they write*, not by their role in the pipeline: `best-of-n-reviewer` (code candidates, `best-of-n.ts`) both picks a winner and, on `synthesize`, merges the candidates' implementations into the original worktree — it has to judge *between* implementations it did not write, which is the open-ended part `execute` itself lacks, hence the top rung. `best-of-n-file-reviewer` + `best-of-n-synthesizer` (markdown candidates, `best-of-n-files.ts`) only pick and splice documents, so they sit two rungs down at opus/low. Step type names track their system-prompt file names (`best-of-n-reviewer` / `best-of-n-file-reviewer`).
- **Coordinator contract audit** — the coordinator (`coordinator.ts`) is the only agent allowed to read every repository: the per-repo planners are explicitly forbidden from it and defer cross-repo questions as `[CROSS-REPO]` placeholders. That makes it the last cheap chance to catch a contract mismatch, so its prompt requires auditing **both sides** of every boundary-crossing field along the dimensions that break at the wire rather than at compile time — cardinality (including a producer that collapses a list, which makes any consumer requirement about "all" or "most recent" unsatisfiable), nullability/sentinels, ordering guarantees, timestamp encoding (*including what fixtures and mocks emit*, since a mock in a different encoding makes the behavior untestable), ID types, and one-sided prefix/format normalization. It must also flag any `## Acceptance Criteria` item the contract cannot satisfy under `## Coordination` and recommend amending it or moving it to `## Non-Goal`, rather than silently planning around it — the same class of defect the **criteria feasibility gate** catches later, but here it can still be fixed before the executor freezes a guess in.
- **The plan review is applied, not filed** — `Review TODOs` (`pipelines/actions/review-todos.ts`, on the init and create-todo paths) is the only review that runs *before* any code exists, which makes it the cheapest place in the pipeline to fix a defect: a finding costs a TODO edit instead of an Execute + Review cycle. Its verdict is therefore structured (`TODO_REVIEW_SCHEMA` in `reviewer.ts`, read by `parseTodoReviewVerdict`) and **every finding exits as either a TODO amendment or a `[!]` blocked item**, applied by a trailing reviser child in the same phase (`UPDATE_TODO` step, reusing `buildUpdaterPrompt` with `buildTodoReviewResolutionInstruction` as its `instruction`, and update-todo's `Edit(TODO-*.md)`-only `allowedTools`).

  It used to emit free text — `STATUS: HAS_ISSUES / BLOCKING: n / UNCLEAR: n` — that **nothing parsed**: the phase returned `results.every(Boolean)`, i.e. whether the children exited 0, and the TODO file was never amended. So the one review whose findings were free to act on was the one review whose findings were discarded, while every other review's findings become gate asks. On the run that motivated this, all four `UNCLEAR` items were later rediscovered downstream at full price: one *was* the cycle-1 gate's request to fix a nullable-href regression (35 min and one Execute phase later), another was the finding that stopped the run at cycle 3/3 with no PR (84 min later), and a third — a layout change reaching a second route — was never rediscovered at all.

  Three prompt rules follow from that failure and belong together. The reviewer checks each item's target against the README's `## Non-Goal` (the plan had prescribed a shared-helper extraction into a screen the README excluded, and the old `Alignment` axis — "FAIL if doesn't contribute to objectives" — cannot see that). It flags an item whose `Verify` only a human can run, so the item says so explicitly and later phases treat it as a handoff rather than reporting missing automated coverage for it — which is the **Suggestion budget**'s coverage loop closed on the planning side, where it is cheap. And a `risk` finding must be stated as the defect rather than as a question, because the regression above *was* found here and phrased as "is that behavior change acceptable?", which reads as human-input-required and left the plan unchanged.

  Fails open in every direction: an unreadable verdict leaves the plan as planned, and a reviser that dies falls back to a deterministic append of the findings as `[!]` items (`formatUnresolvedFindingsSection`) so nothing is silently lost. The reviewer is **read-only** — the reviser owns the TODO file, same single-writer reasoning as **Constraint execution has one owner**. Blocking findings go to `emitAsk` only at `interactionLevel: "high"`; a Slack-kicked autonomous run is `"low"`, so the reviser decides. The residual gap: a `[!]` item does not hold a PR (see **A PR means the branch is review-ready**), so a deferred planning question relies on the README verifier's unmet-`(auto)`-criterion check to stop the run.
- **Parallel group concurrency** — Two code paths run a `kind: "group"` phase and each builds its own `Semaphore`: `runGroupPhase()` (`phase-runners.ts`) for top-level group phases, and `ctx.runChildGroup()` (`context-builder.ts`) for groups run from inside a function phase — which is the path `autonomous` takes via `runSubPhases`. Both size it from `getMaxGroupConcurrency()`; they previously held independent hardcoded `5`s, so raising one left the other path capped. The semaphore is **FIFO and children start in array order**, so array position decides start order whenever the fan-out exceeds the limit. That makes ordering a real scheduling decision: `review.ts` deliberately `unshift`es `review-cross-repository` to the front because it is the longest-running child of the set but must be built last (it needs every repo's diff from the per-repo loop).
- **Incremental review scope** — a review is scoped to the branch's own work **since the last review**, not to `origin/<base>...HEAD` every time. `review.ts` records each repo's HEAD into `artifacts/reviews/<ts>/baseline.json` (`workspace/review-baseline.ts`) before any child runs, and the next review reads the newest baseline strictly older than its own timestamp — strictly, because `prepareReviewDir` has already created the current session's directory, so `<=` would make a review its own baseline. `getIncrementalChanges()` (`workspace/pr.ts`) then hands the code reviewer two tiers: the full branch diff stat and commit log as **Change Context (do NOT review)**, and `<sinceSha>..HEAD` as the **Review Target**. The reviewer reports on the target and may read anywhere for context; a defect *outside* the target that the target's code *causes* is still a target finding.

  The reason is the same diff-widening mechanism behind the **Suggestion budget**, one level up: a fresh reviewer pointed at a 12-commit branch every cycle keeps finding pre-existing defects in code the run never touched, and the Must/Should-Fix audit turns each into another cycle. That is how a run whose instruction was only "address the PR review comments" reached cycle 3 — the instruction reaches just the leading `Update TODOs` phase (`autonomous.ts` replaces it with the gate's `fixableIssues` from cycle 1 on), and neither `review.ts` nor the gate ever sees it, so the run's actual scope is the README contract plus the whole branch.

  The range is restricted to paths the branch itself touches, because `<sinceSha>..HEAD` also contains whatever a mid-run `origin/<base>` merge brought in — on the branch this was built for, 10 of 12 commits in that range belonged to other teams. A file both sides changed stays in scope, which is where a merge resolution lands. The baseline is dropped (→ full-branch review) when it is no longer an ancestor of HEAD, i.e. after a rebase or force-push.

  What deliberately stays full-scope: **constraint verification** (whole repo, with merge-base comparison — the only regression net for breakage outside the diff), **README verification** (the done contract is the whole contract, and it is a bounded enumerated list), and the **first review of a branch**, which has no baseline. The accepted cost: a non-local defect in old code that earlier reviews missed will not be found by a later cycle, and goes to the PR for a human instead.

  **The cross-repository reviewer is scoped too, by the boundary rather than by the file.** It was the one child exempt, on the reasoning that narrowing a non-local-mismatch hunt defeats it — and the exemption is what a run pays for on the third cycle. Measured on the run this was written for: the producer repo had **zero** commits on the branch, the consumer's target was one commit narrowing a middleware, the per-repo reviewer correctly reported no Critical and no Warnings, and the cross-repo reviewer — reading the whole contract surface for the third time, and saying so itself in its report ("verified field-for-field in the previous cycle and **has not moved**") — filed a Warning about a React key written in cycle 1, in a file no cycle since had touched. That was the run's last cycle, so it stopped with no PR. The full-scope reviewer's own output is the evidence the scope was wrong: it re-derived a boundary it had already cleared twice.

  So `review.ts` hands each entry in `crossRepoInputs` the **same `reviewScope`** the code reviewer gets, and the prompt applies a different rule to it. The **whole branch stays in the prompt** for every repo — a contract mismatch is judged against both sides as they now stand, never against a diff, so unlike the per-repo reviewer this *adds* a `New Work` block rather than replacing the branch with a range. A boundary is in scope when **either** side appears in one; a boundary whose two sides have both been untouched since that review was already judged then, by a reviewer with the same two worktrees in front of it. Reading stays unrestricted, because most of what establishes a mismatch is unchanged by definition. When every repo reports a usable range and none of them moved, the prompt says so outright and asks for nothing but the recurring findings — no boundary between unchanged sides can newly have broken. That claim needs *every* repo to have a range: a repo whose baseline git rejected has no scope, is fully in scope, and must not be read as unchanged (`boundaryScopeSection`, `cross-repository-reviewer.ts`).

  The accepted cost is the same one the per-repo narrowing takes, and it is not hypothetical — it is exactly the finding above: a cross-repo defect that the cycle-1 reviewer missed while it had full scope will not be found by cycle 3 either, and goes to the human on the PR. What is bought is that a cycle is not spent re-deciding a boundary two earlier cycles cleared.

- **A failed fetch does not abandon repository setup** — `setupRepository`'s initial `git fetch --all --prune` retries (`FETCH_RETRY_DELAYS_MS`, 3 attempts) and, when every attempt fails, warns and proceeds on the refs already on disk. A fetch of a busy repository fails for reasons that are not about this workspace and fails *after* updating most refs: a ref that moves mid-fetch (`incorrect old value provided`) clears on a retry, while a remote carrying two refs that differ only in casing cannot be stored on a case-insensitive filesystem at all and so fails every attempt — retrying alone would not have salvaged the run this was written for, where one manifest repo's fetch failed on 2 of 3 consecutive tries and took the whole `Ensure repositories` phase down with `Failed to set up: …. Check README.md and try again.`, naming the one file that was not the problem. Proceeding is safe because the worktree is cut from `origin/<base>`, which is either present — at worst a few commits stale, which is what branching from a slightly older base means — or missing, and `worktree add` fails loudly on a missing ref. Cloning stays fatal: an absent repository has no refs to fall back on. The warning carries the `error:` / `fatal:` lines rather than the head of stderr, since git reports the reason *after* its transcript of ref updates and a repo with thousands of branches buries it hundreds of lines down.

- **Re-reviewing a pull request that moved** — a review-type workspace exists for a PR someone else keeps pushing to, and everything needed to review it twice was already here **except the fetch**: `setupRepository` checks the worktree out once and nothing moves it afterwards, so a second review re-read the commit the workspace was created at. `refreshFromRemote` (the review API's flag, the operation panel's `Re-review` split-button item, and the Reviews tab's banner) prepends a **`Refresh worktrees`** phase that fetches and fast-forwards each worktree onto the branch it tracks (`actions/refresh-worktrees.ts`, `workspace/worktree-refresh.ts`). **Incremental review scope** then does the rest by itself — the baseline says what the last review judged, so the range is exactly the commits the author pushed since.

  Three things decide the shape. It is **deterministic TypeScript, not an agent instruction**: each state has one right answer, and the rewritten-upstream case needs `git reset --hard`, which the managed `blockDangerousBash` hook stops an agent from running at all. It is a **phase, and the review is built inside a second phase after it** (`buildDeferredReviewPhase`), because a review's diff, scope and baseline are all resolved while the pipeline is *built* — a refresh that ran as the review's own first phase would move HEAD after the range had been computed from it. `refreshFromRemote` is therefore handled by an early return at the top of `buildReviewPipeline`, before `prepareReviewDir` creates a session directory. Best-of-N is the exception that needs no wrapper: it already builds both its candidate and its fall-back phases lazily, so the review route prepends the refresh phase alongside them instead of passing the flag down.

  It is **opt-in**, and never on for `autonomous`: on a workspace whose branch the pipeline itself is writing, moving HEAD onto the remote is the wrong thing to do. And it is **best-effort** — a dirty worktree is never mutated (discarding a human's uncommitted work to make a review current is not a trade this makes on its own), a failed fetch still fast-forwards onto a locally-known newer upstream, and the phase returns success in every case, because failing would abort the operation before the review and a review of a slightly older commit beats no review. What it costs is that the "we reviewed the wrong commit" case is reported rather than prevented, which is what the phase result and the `staleWorktree` badge are for. A reset saves the discarded head to `refs/aiw-refresh-backup/<sha>` first, since "upstream was rewritten" and "we have local commits" are the same shape from inside the worktree.

  **The banner is the entry point, and it compares two things that already existed** (`workspace/review-freshness.ts`, `GET /api/workspaces/[name]/review-freshness`): `baseline.json`'s per-repo HEAD against the PR's `headRefOid`, read through the same TTL cache the Pull Requests tab uses. `updatedSinceReview` and `worktreeStale` are kept separate because they call for different things — the first is why to re-review, the second is what would make that re-review read the wrong code. Absence never counts as a difference: no PR, no baseline, or an unreadable worktree reports "nothing to say", or the banner would be permanent on every workspace without a PR.

- **A base branch that moved is merged back in, and only the conflicts go to an agent** — `resolve-base-conflicts` (the **Solve PR base branch conflicts** button on the TODO tab's forms, `solve-base-conflicts-button.tsx`) takes each open PR the worktrees have, merges its base back in with `git merge --no-ff`, hands whatever conflicts to one agent per repository, then commits and pushes. A worktree is cut from `origin/<base>` once and never moves, so this is the state every PR drifts into on its own while its base advances — and unlike **Re-reviewing a pull request that moved**, which fast-forwards onto the *same* branch, this one writes a merge commit and pushes it.

  The split is the whole design. Everything with one right answer is deterministic TypeScript in `workspace/base-merge.ts` behind the same injected `GitExec` seam as `worktree-refresh.ts`: fetch, merge, check, commit, push. The agent (`conflict-resolver.ts`, `RESOLVE_CONFLICTS` step, opus/medium) is handed exactly the part that needs judgment — the merged content of the files git named — and is forbidden to commit or push, so **`finalizeConflictedMerge` always runs between a resolution and someone else's PR**. It reads git rather than the agent's report: a path left unmerged, or a conflict marker still staged in one of the conflicted paths (`git grep --cached`, scoped to those paths so a document about merges is nobody's business), rolls the merge back with `git merge --abort` instead of committing. An agent that committed anyway — its prompt forbids it, the tool grants cannot prevent it — is accepted rather than re-committed, since MERGE_HEAD is gone and the index is clean.

  Four refusals decide the rest. **A worktree not on the PR's `headRefName` is left alone**: the push targets the branch the PR is open on, so merging elsewhere would put this branch's commits on that PR. **A merge already in progress** belongs to whoever started it, and its index is the one thing the resolver reads. **A dirty worktree** is never merged into, same trade as the refresh phase. And **a merge that failed with no unmerged paths** is rolled back — that is git refusing for another reason, not a conflict, and a half-merged worktree strands every later phase. A failed fetch is *not* one of them: a locally known `origin/<base>` is stale at worst, and `rev-parse --verify` is what decides whether there is anything to merge. The push carries no force flag of any kind, so a rejection is reported rather than resolved.

  It is one function phase rather than merge → resolve → push, because the children are only known once the merges have run and a mid-merge worktree must not outlive an `appendPhases` boundary. It is **not** wired into `autonomous`, and it is disabled while any operation runs on the workspace — a merge landing under a running executor is the same hazard the refresh phase avoids by being opt-in. The accepted cost, stated in the phase result rather than implied away: **nothing here runs the repositories' lint / test / build.** The PR's own CI runs against the pushed merge commit, and the Pull Requests tab already triages a red check into a fix.

- **A review a human starts verifies the comments already on the PR** — `carryPostedFindings` (set by the review route, never by `autonomous`) collects every finding this workspace posted and grounded (`workspace/posted-findings.ts`, reading `finding-groundings.json` plus the `FINDINGS-*.json` of the session that produced each one) and hands each repository *its own* asks to the existing `verify-fixes-<repo>` child. Re-reviewing without it asks "is this code good?" of a branch whose author has been answering "did you do what I asked?" — and the machinery for the second question was already built for the autonomous cycle.

  The two ask sources are **never merged**: a gate ask is one the gate may later retire, while these were written by a human onto someone else's PR and only the author can settle them, so `requestedFixes` takes precedence and `askSource` tells the verifier's prompt which it is holding (a declined PR comment is answered in the thread, not in a TODO file). Asks are grouped per repository — a verifier reading another repo's comment can only report it absent — and sorted by path and line, so the numbering in its report is stable between runs.

  **The declined findings go to the known-findings ledger** (`knownFindingsFromGroundings`, `post-review-findings.ts`), which otherwise has no writer outside the autonomous gate: a workspace that only ever reviews re-derived and re-reported at full length exactly the findings a grounding pass had already checked and dropped. A refuted or unsettled claim is `low-confidence`, a confirmed `pre-existing` or `local-only` one is `pre-existing`. The filter is `shouldPost`, **not** `posted`: a finding that earned a comment and failed to reach GitHub is still an ask the human wants made, and listing it would tell the next reviewer to compress it to a `(Recurring)` line.

- **Toolchain pre-warm** — `git submodule update --init` and the dependency install are the slowest commands in a fresh worktree (240s and 20s measured on one run, 4.3 of the 12 minutes of the first executor child), and they used to run *inside* Execute, on the critical path. Nothing between repository setup and Execute needs them: constraint discovery, TODO planning, the plan review and the README gates read source and write markdown, and on that run they took ~16 minutes. So `buildInitTodoAnalysisPhases` inserts a fire-and-forget **`Prepare toolchain`** phase right after `Discover repo constraints` — the first point at which the commands are known, since it reads them from the README the discovery phase just wrote — and `execute.ts` awaits the result before spawning any executor (`workspace/toolchain-prewarm.ts`, promises keyed by workspace+repo on `globalThis`). Only labels that touch the *environment* are pre-warmed (`Toolchain`, `Install`, `Submodules`, `bootstrap`, …); `Codegen`, `Format` and `MSW` are deliberately excluded, because the planner and plan reviewer are reading that worktree while this runs and a diff appearing underneath them belongs to the executor. Failure is **reported, never fatal** — the executor resolves its own toolchain regardless (`TOOLCHAIN_RESOLUTION`), so a failed prep costs the time this was meant to save and nothing else. A standalone `execute` run simply finds nothing registered.

- **Requested-fix verification** — when a cycle's gate sets `fixableIssues`, the next review spawns a `verify-fixes-<repo>` child (`fix-verifier.ts`, `VERIFY_FIXES` step, opus/low) writing `VERIFY-FIXES-*.md`: one status per numbered ask, `LANDED` / `PARTIAL` / `NOT LANDED`, read out of the code. `autonomous.ts` reads the asks from `gateHistory` at **run** time, not build time, since later cycles are appended before the gate that fills their entry has run. It is a separate child from the code reviewer on purpose — same reasoning as **Constraint execution has one owner**: the "did the ask land" verdict and the "is this code good" verdict belong in different files with different scopes, and the prompt forbids it from reporting quality findings at all. It replaces inference from TODO checkboxes, which record what the executor *believed*: the gate prompt now states the verifier outranks its own TODO cross-reference where they disagree. `NOT LANDED` / `PARTIAL` on an ask the gate still stands behind forces `shouldLoop: true` regardless of cycle number — the Suggestion budget governs *new* findings, not work already requested and lost — but the gate may **retire** an ask into `dismissedFindings` when the verifier quotes a recorded reason it was declined, since the gate wrote it and is the only one who can withdraw it. The collector carries these statuses into `SUMMARY.md`'s top priority list and keeps them out of the severity counts, because a status says whether requested work happened, not whether code has a defect.

- **PR review threads are answered by the phase that pushes** — the "Address PR Reviews" quick-fill (`address-pr-reviews.ts`, filling the TODO update form → `autonomous` with `startWith: "update-todo"`) triages each review comment into a TODO item, and also records it as a table row under `## PR Review Threads` in the TODO file: GraphQL thread node id, comment URL, summary, and the TODO item's first line verbatim. It is forbidden from replying or resolving itself — at triage time the fix does not exist. `create-pr.ts` reads that section back (`extractPrReviewThreadsSection`, `todo.ts`) and hands it to the PR creator, which after a **successful push** replies to and resolves each thread whose item is `[x]` or gone from the file, and leaves `[ ]` / `[~]` / `[!]` threads untouched with no comment at all. That is the "未完了ならやらなくていい" half: an incomplete item's thread stays open for the human on the PR.

  Three constraints decide the shape. The **executor cannot do it** — its prompt forbids `gh pr view` / `gh api` and any push, so it never knows a fix reached the remote (`executor.ts`, Scope Boundaries). The **record must survive `stripCompletedTodoItems`**, which runs at the start of every cycle's `Update TODO` and deletes exactly the `[x]` items worth replying about — hence non-checkbox table rows, plus an explicit rule in the updater's prompt not to delete the section (the cycle updater receives only `fixableIssues`, so nothing else tells it the section matters). And **idempotency comes from GitHub**, not from writing state back into the TODO file: the creator skips any thread already `isResolved`, so a re-run or a resumed `Create PR` cannot double-post. Absence of an item is read as complete rather than as missing, because by create-pr time deletion is the *normal* end state of a finished item.

  The reply is written from the pushed code — what changed, where, and the carrying SHA — not from the TODO item's wording, since the item says what was asked for. Under `autonomous` the whole thing only ever runs when the gate cleared the Completion Bar, so a run that stops at `maxLoops` replies to nothing. A standalone `create-pr` on a workspace whose TODO has no such section behaves exactly as before: `buildPRCreatorPrompt` omits the section and the system prompt's procedure is gated on its presence.

- **A task's PRs share one title** — a new PR's title is the README's `# Task:` heading, handed to every repository's child verbatim (`resolveSharedTitle` in `create-pr.ts` → `sharedTitle` → the prompt's `## PR Title` section). The children of the `create-pr` group run in parallel and each sees only its own repo's diff plus the README, so with the old *"compose a concise title"* instruction one task's PRs reached a reviewer under N unrelated titles — nothing in the fan-out could align them. The heading is the only title the workspace already has, computed once by `init-readme` and free to reuse, which is why the fix is deterministic rather than another model call.

  Three bounds. The mandate covers the **descriptive part**, so a prefix the repository's own convention requires (`feat: `) may precede it; appending the repo name is forbidden, since it breaks the byte-identity that makes the set recognizable and the PR list already names the repository. A **placeholder heading is rejected**, not mandated — a README that `init-readme` never rewrote still carries the template's `TBD`, and `parseReadmeMeta` reports a missing heading as `Untitled`; either falls back to composing. And an **existing PR never receives it**, because the update path retitles only when scope shifted and the current title may be the user's own wording. `init-readme`'s heading limit is 70 characters rather than 80 for this reason: a title that cannot be used verbatim is one the agent shortens, which is where the divergence came back.

- **A PR body is an overview, and the diff is the detail** — `### PR Description: An Overview, Not a Walkthrough` (`pr-creator.ts`) bounds the description to the change's rough shape in a few sentences, generally under 10 lines for the descriptive part (a template's headings and ticket links excluded). The rule it turns on is that **anything a reviewer would answer by reading the diff belongs to the diff**: the body exists so they know what they are looking at before they open it. Bullets past the overview are for what the diff cannot show and they would otherwise be surprised by — a deliberate trade-off, deferred work, a migration or rollout step. The bar is carried by a **worked example of a finished body** rather than by prose about length, since "concise" alone doesn't locate an altitude.

  There was no length rule here at all: every other report-writing agent carries `WRITTEN_DELIVERABLE_LENGTH`, and the one whose deliverable a *human* reads had nothing. Four instructions then supplied the padding, each now inverted rather than merely capped. The Guidelines' *"Include all commits in summary, not just the latest"* was written against summarizing only the newest commit but reads as an instruction to enumerate, so a multi-cycle branch's body became a changelog — it now asks for one description of the **final state**. The update path listed *"summary, implementation details"* as the sections to refresh, naming the walkthrough as a thing the body has. Its *"reflect the current full set of changes"*, applied to the existing body as its base, grew the body once per cycle — it now **replaces** those sections rather than appending. And the full workspace README is inlined in the user prompt as context, which makes copying its Goal / Requirements / Acceptance Criteria the shortest path to a filled-looking body; those are named as not-body-content, with one sentence of purpose drawn from it being enough.

  A provided PR Template is the one thing this does not shorten: every section it requires still gets filled, since the repository chose that structure. The bar governs what goes *inside* them — a section with nothing substantive gets one line or `N/A`, never a paragraph written around the absence.

- **The Pull Requests tab is where a human decides, per comment or per red check** — the workspace's `pull-requests` tab (`pull-requests-view.tsx`, `pr-review-thread.tsx`) lists the PR on each worktree's **own branch** — the same PR `checkExistingPR` looks for, read by `listWorkspacePullRequests` (`workspace/pr-threads.ts`) via `gh pr view` plus one GraphQL query — and gives every review thread a checkbox and two buttons. Both act on a multi-select, and both are the *human's* call: **validate** for "I can't tell what this comment means", **triage** for "yes, this needs doing".

  **CI rides along in the thread query rather than in a second call.** The same GraphQL document asks for `statusCheckRollup` on the last commit, so `gh pr checks` — another process spawn and another network round trip per repository — is never run. `parseStatusChecks` maps GitHub's two unrelated vocabularies (a CheckRun's `status` + `conclusion`, a legacy StatusContext's single `state`) onto one `PrCheckState`.

  What that mapping must **not** do is over-collapse, and the first version did: it folded every non-`COMPLETED` status into one `pending` bucket whose UI label read "running", so a `QUEUED` job was displayed as running work with logs to go read. `queued` and `running` are therefore separate states — `IN_PROGRESS` is running, `QUEUED` / `WAITING` / `PENDING` / `REQUESTED` are queued, and a status GitHub adds later also lands on `queued`, because the one property that has to survive an unrecognized value is *not finished*: calling it `unknown` would let the headline say everything passed with a job still outstanding. On the legacy side the same distinction exists with inverted spelling — a commit status's `PENDING` is posted when CI picks the work up (running) while `EXPECTED` means no status was posted at all (queued). Finished-but-not-passed states stay distinct too: `TIMED_OUT` / `ACTION_REQUIRED` / `STARTUP_FAILURE` are `failure` (none passes on its own), `SKIPPED` and `CANCELLED` are themselves, and `NEUTRAL` / `STALE` are `unknown` — none of them counted as a pass. The summary carries `counts: Record<PrCheckState, number>` rather than a chosen subset so a new state cannot leave checks uncounted, and the headline reads failing → running → queued → passed → **"no result"** when only skipped/cancelled/unknown remain.

  Failures sort first and auto-expand, since they are what needs acting on; in-flight checks do not, because they resolve themselves and the badge already gives the count. An **absent rollup is `reported: false`, rendered "CI: unknown"** — no CI configured is not everything passing, and a thread-query failure leaves the PR visible with exactly that state rather than an accidental green.

  **A red check is triaged like a comment, and its log travels in the instruction.** A `failure` row carries a checkbox (`isTriageableCheck`, `pr-checks-summary.tsx`) and joins the same multi-select the threads use, so one Triage can carry both kinds. `failure` only: a `queued` or `running` check has no verdict yet, and `skipped` / `cancelled` / `unknown` were never run to one, so ticking any of them commissions a fix for a failure nobody has seen.

  What the selection has to carry is the **log**, because nothing downstream can go and get it — the updater's `allowedTools` are `Edit`/`Write(TODO-*.md)` plus `Bash(git:*)`, and the executor's prompt forbids `gh run view` outright and works from the "failing job name and its key error line" the item is required to quote. So Triage first POSTs the ticked checks to `/api/workspaces/[name]/pr-check-logs`, which reads each with `gh run view --job <id> --log-failed` (falling back to `--log`, for a job that died before a step printed anything) and returns a tail: last 150 lines / 10k chars, gh's `<job>\t<step>\t<timestamp>` line prefix stripped (`workspace/pr-check-logs.ts`). The **tail** rather than the head because a runner prints the failure it stopped on last, where a head slice is setup output. A POST on click rather than a field on the tab's GET for the same reason that read is TTL-cached: a log costs a `gh` round trip per check and nobody reads it until they decide to act, while the GET runs on every mount and focus.

  Three things follow. **An unreadable log does not block the triage** — a `gh` failure, or a check whose details url points at an external CI (`parseCheckRunRef` returns null), comes back as a `reason`, and the instruction renders "No log could be read" with a direction to reproduce locally and mark the item `[!]` blocked if it cannot; a run that has to reproduce beats no run. **Validate is disabled for a check-only selection**, since it interprets a review comment and a check has none — this is where the two buttons stop being the same decision at different confidence. And the CI half of the instruction keeps a **flake/infra outlet**: if the log shows the failure is not this branch's (runner outage, missing secret, unrelated flake, breakage already on the base), no item is written — it goes under `## Notes` with no checkbox. That is the one judgment left to the run, because a human can see that a check is red without being able to see why. CI items get **no `## PR Review Threads` row**: there is no thread behind a check, so a row would hand `create-pr` something to reply to that does not exist.

  **The read is TTL-cached, because it is the expensive part.** A cold read costs two `gh` round trips *per repository* and nothing renders until both return, while SWR revalidates on mount and on focus — so switching browser tabs or having the page open twice paid it again for data that changes at the pace of a human writing a comment. `pr-cache.ts` keys a **promise** per workspace on `globalThis` for `PR_CACHE_TTL_MS` (60s), so the TTL and in-flight coalescing fall out of the same entry: two tabs loading at once share one round trip. A **rejection is never cached** — a per-repo failure resolves into `problems`, so a rejection means the workspace itself could not be listed, and holding that for a minute would keep reporting an error the user already fixed. The cost is that a comment or CI result from seconds ago may not appear yet, which is what the tab's Refresh button is for: it sends `?refresh=1`, the one thing that reads past the cache. Validations are deliberately **not** cached (local, cheap, and a just-finished validate must show immediately), and **operations never read through the cache at all** — `validate-pr-comments` resolves thread ids against the live PR precisely so a thread GitHub has since resolved is skipped rather than trusted.

  The two buttons are the same decision at different confidence, so they compose rather than branch. **Validate** starts the `validate-pr-comments` operation (`pipelines/validate-pr-comments.ts`): one read-only child per selected thread (`pr-comment-validator.ts`, `VALIDATE_PR_COMMENT` step, opus/medium), each returning `verdict` ∈ `valid` / `invalid` / `unclear` plus interpretation, reasoning, recommendation and `file:line` evidence, merged into `artifacts/pr-validations.json` (`workspace/pr-validations.ts`) and rendered inline under the comment. **Triage** builds `buildTriagePrCommentsInstruction` and posts `autonomous` with `startWith: "update-todo"`, which is what makes the **validate → triage route** work: a recorded verdict is folded into that instruction verbatim, so the run starts from the analysis instead of re-deriving it. Triaging is not gated on having validated, and triaging past an `invalid` verdict is allowed — the instruction says the override was deliberate, since the human saw the verdict and chose to act.

  **The selection also decides which worktrees the run touches.** When every selected thread and check belongs to one repository, Triage passes that repository as autonomous's `repo`, which reaches `stripCompletedTodosFromWorkspace`, `buildUpdateTodoPipeline`, `buildExecutePipeline`, `buildReviewPipeline` and `buildCreatePrPipeline` (`autonomous.ts`) and filters each to that one worktree — and, via `review.ts`'s `!repository && repos.length > 1`, drops the cross-repository reviewer, which has no boundary to judge when only one side can move. Without it, one comment on one repository spent a full Execute + Review on every other worktree in the workspace and could open a PR on each; that is the same diff-widening cost the **Suggestion budget** and **Incremental review scope** exist to bound, arriving through the fan-out instead of through the diff. `repo` is a **single value**, so a selection spanning repositories cannot be expressed and deliberately falls back to the whole workspace rather than silently triaging a subset — which is also the honest behavior, since a cross-repo comment set is exactly where the cross-repo reviewer earns its place. The action bar states the scope (`· <repo> only`) because nothing else on the page says which worktrees a Triage will touch.

  Four things fall out of that being a *human* decision. The validator is **read-only by construction**, not by prompt alone: setting `allowedTools` at all replaces the Edit/Write grants `addDirs` would generate, so its `["Bash(git:*)", "Bash(gh pr view:*)"]` leaves it unable to write, and `gh` narrowed to `pr view` puts every mutation out of reach. `unclear` is a **first-class verdict** rather than a failure — the button exists because a human could not tell, so an agent that picks a side to look decisive makes it a coin flip; a child returning no parsable verdict stores nothing at all, since `unclear` is itself a claim ("the code cannot settle this"). Verdicts are **persisted** because the point of validating is deciding afterwards, and a reload must not lose it. And triage is scoped to the listed threads and told **not to re-judge** them — the contrast with the "Address PR Reviews" quick-fill above, which starts from a PR nobody looked at and judges validity itself.

  One child per thread rather than one per PR is a deliberate cost trade: the per-PR call is cheaper on context but treats the tenth comment as an afterthought, and each verdict here decides whether a human spends a whole autonomous run. They are independent, so they also run concurrently under `getMaxGroupConcurrency()`, which keeps wall clock near a single comment; the phase budget is therefore per selected thread (`validatePrCommentsBudgetMs`), because the concurrency cap makes a large selection queue. Both buttons are disabled while any operation is running for the workspace — a validate would judge a worktree the executor is editing. Threads are resolved against the live PR at run time, so an id the tab showed and GitHub has since resolved is skipped rather than trusted, and `maxRetries: 0` because the verdicts already written are durable and re-running the whole fan-out costs more than a second click.

- **A selected finding is a candidate, and the grounding pass decides what gets posted** — the review tab lists every finding the code reviewer recorded with a checkbox; the ticked ones start the `post-review-findings` operation, which spawns one read-only agent per finding to check the reviewer's claim against the pushed code, and posts only what survives (`review-findings-list.tsx`, `pipelines/post-review-findings.ts`, `finding-grounder.ts`, `GROUND_FINDING` step, opus/medium). The list is deliberately **complete** and the human's tick chooses *candidates*: `REVIEW_COVERAGE_POLICY` has the reviewer report everything — including findings it is unsure of — precisely so filtering happens downstream, and nothing downstream did that for outbound comments. A human ticking rows cannot cheaply confirm a mechanism, so this is the missing filter. Pre-ticked is Critical and Warning at medium confidence or better (the autonomous gate's own loop bar), plus nothing a previous run already declined.

  It is the **outbound mirror of `validate-pr-comments`**: that one checks a claim arriving from a reviewer, this one checks a claim about to leave. The asymmetry that decides the prompt's wording is that **nobody reads this verdict in between** — the operation grounds and posts in one action, so a wrong `yes` reaches a stranger's PR unread. Hence the bias toward silence: refuting a finding is a success, `unclear` is a real answer, and both `normalizeHolds` and `normalizeScope` fall back to values that **do not post**, so an unparsed field can never be what publishes a comment. It is also forbidden from reporting anything else it notices — a finding nobody selected is a comment nobody asked for.

  Two axes have to clear, and the second is the one this exists for. `holds` asks whether the mechanism is real in the code as pushed. `scope` asks whose problem it is: `pr`, or `local-only` — an artifact of *this checkout*, which the prompt has it check with `git status --porcelain`, since a comment about uncommitted work describes code the author does not have — or `pre-existing`, real but untouched by the branch. A confirmed defect that predates the branch is still not this PR's business, and it goes on the record instead of onto someone else's review.

  **The comment is written in the target repository's conventions, not this workspace's.** That is not a nicety: `code-reviewer.ts` fixes its output to English *regardless of the README's language* because downstream agents read it, so verbatim posting would put English comments on a repository that reviews in Japanese. The convention evidence is the PR's **own existing review comments**, quoted into the prompt from the `REVIEW_THREADS_QUERY` the Pull Requests tab already runs — actual samples rather than a guess — bounded to 6 comments / 1200 chars because this is a style sample and a long thread would crowd out the finding being judged. Falling back: `CONTRIBUTING.md`, the PR template, recent commit messages, then English. `buildCommentBody` therefore prepends **nothing** — no `**Warning**` label, no `(confidence: low)` note — since either would undo exactly what the pass is for; urgency is the comment's job to convey in the repository's words.

  **The children never post.** They have no write tools (`allowedTools: ["Bash(git:*)", "Bash(gh pr view:*)"]` replaces the Edit/Write grants `addDirs` would generate) and the trailing deterministic phase does the posting from their structured output. That keeps one review per repository rather than one notification per finding, keeps the marker-based idempotency in one place, and means no agent ever holds a mutation on someone else's PR. Verdicts are persisted to `artifacts/finding-groundings.json` (`finding-groundings.ts`) because the decision outlives the operation: a later visit shows which findings were dropped and why, and a declined finding is not re-ticked — re-grounding it every visit would spend a child to reach the verdict already on the row. A child that returns no parsable verdict stores **nothing**, so the finding stays re-runnable rather than recorded as a considered `unclear`.

  This needs a **second deliverable**, because a checkbox needs a discrete object with a stable id and a report's prose bullets have neither — nor a `path`/`line` a comment could be anchored to. So the code reviewer writes `FINDINGS-<org>_<repo>.json` next to its `REVIEW-*.md` (`review-findings.ts`, prompt section `### The Findings File`), with the JSON `body` written **for a PR reader** rather than copied from the report. Parsing is fail-soft in every direction: a review whose findings file the model mangled, or one from before this existed, renders its markdown and simply cannot be posted from. An unknown severity falls to `suggestion` and an absent confidence to `medium` — the first because guessing `warning` would pre-tick a comment onto a stranger's PR on an unparsed label, the second because that is the rule the gate already applies to a review report.

  **The anchor is resolved before the human chooses, not at post time.** GitHub rejects an inline comment whose line falls outside a diff hunk, so `diff-anchors.ts` parses the same three-dot diff GitHub computes and grades each finding `inline` / `file` (file-level, still requires the file to be in the diff) / `pr-body` — the row says which, so a selection of six does not come back as four successes and two 422s. Context lines count, since GitHub's diff carries three on each side. Nothing is dropped by the grading: the review body is where a finding about an untouched file still reaches the reader.

  **Idempotency comes from GitHub**, same reasoning as `create-pr`'s `isResolved` skip: each posted comment carries an invisible `<!-- aiw-finding:<id> -->` marker, and a finding whose marker is already on the PR is skipped rather than posted twice. Both the PR's comment list *and* any pending review's own comments are read, because a pending review's comments appear only in the latter — a finding sitting in an unsubmitted review would otherwise be offered again. The marker scan runs over the raw response text rather than parsed JSON, which makes it indifferent to how `gh` frames a paginated result; a missed page would mean a duplicate comment. The finding id hashes only the body's **first line** so a human editing the comment before sending does not change what it matches.

  The review is left **pending** by default (`event` omitted), so the last step before anything reaches someone else's PR is a submit on GitHub; `Submit immediately` is the opt-out. A **pending review already on the PR is reported, not worked around** — GitHub allows one per user per PR, so the request would 422, and "submit or discard the one you have" is more use than relaying that. And the request carries **finding ids only**: everything that decides where a comment lands is re-read server-side from the review's own findings file, and the text comes from the grounding pass, so a client can neither aim a comment at a location the reviewer never named nor choose its wording.

  Posting is disabled while any operation runs for the workspace, since the anchors were computed from a worktree that operation is editing and the grounding children would read it mid-edit; a worktree not at the PR head is badged rather than trusted. Three known gaps: the **cross-repository reviewer writes no findings file** (a boundary mismatch spanning two repos has no single `path:line` to anchor to, so its report stays markdown-only), the finding's own text is **not editable** in the tab (it is the claim the grounder checks, not the comment that gets posted, so an editor there would need to reach the grounding prompt), and the findings GET costs three `gh` round trips plus a `git diff` per repository, which is why its hook does not revalidate on focus and the tab has a Refresh button.

- **Constraint execution has one owner** — during a review, lint/test/build run in exactly one place: the `Verify constraints` function phase in `review.ts`, over the commands the README declares under `## Repository Constraints`. The code reviewer used to discover and run them as well (`code-reviewer.ts` step 4, *"run them. Report any failures as **Critical Issues**"*), which put a second verdict on the same commands into the same `SUMMARY.md` with no merge-base comparison behind it — so a failure that predates the branch reached the autonomous gate as a Critical blocker while the constraint table classified the identical failure as `PRE-EXISTING` and informational. `checkPreExisting()` exists precisely to draw that line, so the reviewer's prompt now defers execution to the phase and keeps only what it can judge from the diff: insufficient test *coverage* as a Warning. (The executor still runs the constraint set while implementing, `executor.ts` — that is the author self-checking before marking a TODO `[x]`, not review evidence.) A repo with no declared constraints still gets a `CONSTRAINTS-*.md` from `buildNoConstraintsReport()` reading `NOT DECLARED`: an absent file leaves the collector's constraint section at `(none)`, which is indistinguishable from a clean run now that nothing else runs the commands. That path is reachable through a hand-edited README or `init --only`, where constraint discovery never ran.

  **A repository added after init is discovered where it is set up.** `Discover repo constraints` used to be built only by `buildInitTodoAnalysisPhases`, so a repo added to a live workspace — `update-readme`'s `Ensure repositories` phase, or autonomous's salvage phase of the same name — got a worktree and nothing else: `Verify constraints` then wrote `NOT DECLARED` for it every cycle, `Prepare toolchain` had nothing to pre-warm, and the planner had no command to put in an item's `Verify:`. `syncReadmeRepositories` therefore returns `setUpRepos` (the new paths resolved to on-disk worktrees, which only the post-setup listing knows) and both phases hand them to `discoverConstraintsForNewRepos`. It cannot be the updater agent's job: that child's `allowedTools` are `Edit`/`Write(README.md)` + `Bash(git:*)`, and discovery's required probe is a tool invocation in the worktree.

  Incomplete discovery is **reported, not fatal**, on both paths — the worktree is what the run actually needs and the executor resolves its own toolchain, so aborting would trade a working run for a missing report. And `buildDiscoverConstraintsPhase` now **skips a repo the README already declares commands for**, because discovery *appends*: without it the autonomous path discovered a salvaged repo twice (`Ensure repositories`, then `Ensure TODOs` for the same repo, which has no TODO file by definition), leaving two `### <repo>` blocks for the constraint runner to execute in turn. A README it cannot read declares nothing, which is the init case, so discovery proceeds.

  Two things make that ownership real rather than nominal. **The declared command has to run.** Constraint discovery was told *"Do NOT run the commands — only identify them"*, so what it recorded was whatever the repo's docs said — and on one workspace every single one of the eight failed in ~280ms, because a bare `pnpm` resolved to a Bun shim in the pipeline's non-interactive `sh -c`. `Verify constraints` then reported 8/8 `PRE-EXISTING` every cycle, which is indistinguishable from a clean run, while the executor rediscovered `mise exec node@22.22.0 -- pnpm` from scratch (13 Bash calls in the first batch, 6 more in the second) and the README verifier re-ran the whole suite and build itself. The prompt now requires a **cheap probe** — `<invocation> --version` for each distinct tool, checked against the repo's version pins — and records the form that passed, exec prefix included. It still never runs lint/test/build: probing the tool costs a second, and running the work is this phase's job.

  **And the phase runs first.** `buildReviewPipeline` returns `Verify constraints` → reviewer group → collect, so the `CONSTRAINTS-*.md` report is on disk while the children work, and `buildReadmeVerifierPrompt` takes its path. A criterion phrased as "lint, typecheck, test and build exit 0" — which is what `init-readme.ts` writes whenever the README references the constraint table — was otherwise verified by re-running all of it, once per cycle, with no merge-base comparison behind it: the same duplicate-verdict problem the code reviewer had, arriving through the verifier instead. Ordering costs nothing in wall clock (the phase is deterministic and the same length wherever it sits) and it is what lets the verifier's prompt forbid the re-run.
- **Phase retries** — Phases support `maxRetries` (default 2) and `retryDelayMs` (default 3000). Per-phase timeouts use separate AbortControllers from the operation-level kill signal. A retry re-runs the phase from scratch on the *same* budget, so a phase that failed by timing out will normally time out again — burning the full budget and re-spawning every Claude child, up to `maxRetries` times. A **user kill** is already excluded: `killOperation` aborts `managed.abortController`, which both the `while` condition and the post-`delay` check test, so no further attempt starts. The retry announcement is emitted *before* the delay, so a kill landing inside that window leaves a `retry N/M` line in the log that never ran — hence the explicit `retry N/M cancelled — operation was interrupted` follow-up. Do **not** try to detect an interruption by matching the CLI's `[Request interrupted by user]` marker: the CLI prints it on any SIGTERM, including the pipeline's *own* timeout kill, so matching it would suppress exactly the retries that exist to recover from a timeout.
- **Workspace archiving** — `workspace_archives` table (migration v4). `POST /api/workspaces/[name]/archive` toggles archive. Dashboard filters via `recentOnly` (skips workspaces older than 1 week) and `includeArchived` query params.
- **README done-contract** — the workspace README (`src/lib/templates/readme.ts`) defines "done" via `## Goal`, `## Non-Goal`, `## Assumptions`, `## Requirements`, and `## Acceptance Criteria`. Because verifier/gate treat these as authoritative, `init-readme.ts` is instructed to ground them in the request (no fabrication), under-specify rather than mis-specify, and record anything it had to guess under `## Assumptions` (the gate treats those as unverified and requires Non-Goal exclusions to be explicit, never inferred). Each Acceptance Criteria item is a checkbox tagged `(auto)` (agent-verifiable with evidence) or `(manual)` (human-only handoff — visual QA, staging sign-off). `parseAcceptanceCriteria()` (`src/lib/parsers/readme.ts`) extracts them (untagged ⇒ `auto`) and `review.ts` / `autonomous.ts` pre-render the split into the README-verifier and autonomous-gate prompts. The verifier classifies `manual` items as `PENDING-HUMAN` (not a failure; satisfaction rate counts only `auto`); the gate loops **only** for unmet actionable `auto` criteria (or Must/Should-Fix findings), never for `manual`/handoff items, and never attempts anything listed under `## Non-Goal` (prod release, irreversible ops). This is what the init prompt (`init-readme.ts`) is instructed to fill.
- **The TODO tab lists repositories, not files** — the tab is rendered from the `TODO-*.md` files on disk (`getTodos` → `listTodoFiles`), so a repository the README declares with nothing planned for it yet had no card at all: a repo added after init was silently absent, and with no TODO file anywhere the tab was the bare `No TODO files found.` string. `TodoUpdater` now diffs the README's `repositories` (already passed for `findRepoPath`) against the parsed files and renders the remainder as a `No TODO file` card whose button starts `autonomous` with `startWith: "execute"` — the path that reaches the `Ensure repositories` → `Ensure TODOs` salvage phases, which plan through the full init analysis (planner → coordinate → `Review TODOs`) and discover the repo's constraints. Deliberately **not** `update-todo`: that pipeline does list worktrees rather than files and its `Write(TODO-*.md)` grant lets it create one, so the file would appear — written by an updater from an empty string, with none of the planning phases and no `[CROSS-REPO]` resolution. Matching is by the path's last segment (the worktree directory name, `___alias` suffix included, which is what `setupRepository` names the file after) with the README alias as a fallback, mirroring `findRepoPath`. The empty state survives only when the README declares no repositories either, and the workspace-wide form still requires at least one TODO file, since it edits files.
- **TODO normalization** — `normalizeTodoCheckboxes()` fixes common LLM formatting errors (missing checkboxes, bracket spacing, asterisk bullets). `stripCompletedTodoItems()` removes `[x]` items before update-todo runs. Both prevent autonomous loops.
- **Memo tab** — Per-workspace `artifacts/memo.md` file with Monaco editor (`src/components/workspace/memo-editor.tsx`). Auto-saves every 60s + on navigation/beforeunload. Module-level content cache prevents stale content on tab switches. Toolbar action on selected text: "Update TODO" (starts update-todo operation). API: `GET/POST /api/workspaces/[name]/memo`.
- **Auto-managed Claude Code hooks** — `src/lib/claude/hooks/sync.ts` writes hook entries into `.claude/settings.local.json` and `.claude/hooks/aiw-*.sh` scripts on every startup (called from `src/instrumentation-node.ts`). Managed entries are identified by the `aiw-` command prefix; user-authored hooks without that prefix are preserved verbatim. Two hooks ship today: `SessionStart` (injects `git branch` + `git status --short` as additionalContext) and `PreToolUse(Bash)` (blocks `rm -rf /...`, `git push --force` without `--force-with-lease`, `git reset --hard`). Toggleable per-workspace via `hooks.sessionStartGitContext` / `hooks.blockDangerousBash` in `config.yml` (both default `true`).
- **Function phase output grouping** — `emitStatus`/`emitResult`/`emitTerminal`/`emitAsk`/`setWorkspace` from a function phase are auto-tagged with `childLabel = phaseLabel` so they render as boxed sections in the operation log alongside Claude child output. `runChild`/`runChildGroup` preserve `phaseExtra` so each child still gets its own label via `wireChild` (`src/lib/pipeline/context-builder.ts`).
- **Slack bot** — Optional Socket Mode bot for `app_mention` events: kick off `init` operations, hold free-form conversations (read-only by default; writes only when explicitly asked), and post completion notifications. See the **Slack bot** subsection below for the full breakdown.

### Slack bot

Optional Socket Mode bot in `bin/slack-server.ts` (started by `bin/start.ts` when `slack.enabled` + both tokens resolve non-empty). Handles `app_mention` events only; mentions from non-allowlisted user IDs (`slack.allowedUserIds`) are silently dropped. Implementation lives in `src/lib/slack-server/` — bare filenames below are relative to it; the `app_mention` handler + `handleConversation` are in `index.ts`.

- **Commands** — `init <desc>` POSTs `/api/operations/autonomous` (`startWith: "init"`, full loop); `init --only <desc>` POSTs `/api/operations/init` (single op, no chain). Both force `interactionLevel: "low"` (Slack is kick-off only; progress + AskUserQuestion follow-ups happen in the WebUI). Anything else (not `init`/`help`) is free-form **conversation** (`parseCommand` → `kind: "chat"`). On accept the bot posts "OK! I'll start your request!"; dispatch failures post "Sorry, failed to start: …".
- **Completion notification** (autonomous only) — when `init` (no `--only`) finishes, a 30 s poller (`notifier.ts`) posts PR URLs back to the thread. Mapping persisted in `slack_pending_notifications` (migration v7). It scans only the `Create PR` phase events (label hardcoded in `pipelines/autonomous.ts`), runs `extractPrUrls()` (`workspace/pr-url.ts`), and subtracts URLs already present in the input description. Posts `Done! Created PRs: …` or `Done! No PRs were created…`. If the run was halted by the **README clarity gate** (`extractClarityGateStop()` finds the gate's stop `emitResult` by phase label + `README_CLARITY_STOP_PREFIX`, both from `templates/prompts/readme-clarity-gate.ts`), it posts that stop reason + update-readme recommendation instead of the misleading "no PRs" message. Failed runs are dropped silently (row deleted, no message). `init --only` is not tracked.
- **Thread link** — a mention inside a thread gets the thread root's `chat.getPermalink` appended to the description via `mergeWithThreadLink()` (`thread-link.ts`, separator `--- Slack thread ---`). The thread body is deliberately NOT inlined (it drowns out the actual request); init/plan fetch the thread on demand. Empty description + permalink alone is accepted. `getPermalink` failure → logged, typed description used as-is.
- **Conversation** (`conversation.ts`) — `converse(threadKey, message)` runs `runClaude` in-process at the workspace root with `skipAskUserQuestion` and **no `allowedTools`/`addDirs`**, inheriting the host's ambient Claude permissions (Bash/git/gh/MCP work wherever the environment allows). The write policy is enforced **only** by the system prompt (`getSlackChatSystemPrompt()` in `templates/prompts/slack-chat.ts`, applied via `appendSystemPromptFile`), not at the tool layer: **read-only on the model's own initiative; writes allowed only when the user explicitly asks** (mainly external MCP actions like "create a Jira ticket", prefer MCP tools); **two hard limits forbidden even on request** — (1) git repository / codebase changes (`git add/commit/push/…`, `gh pr/issue create/…`, editing tracked files, installs, migrations → routed to WebUI/`init`) and (2) destructive/irreversible actions (`rm -rf`, force-push, `git reset --hard`, dropping tables). Keep that prompt precise — and note that a policy of pure prohibition has already produced an undeletable file, see **A requested write has exactly one destination** below. MCP resolves from the workspace-root `.mcp.json`/user scope (per-repo `.mcp.json` is not picked up). Prompt builder `buildSlackChatPrompt()` sends full instructions on the first turn, bare message on resume. Model/effort from `config.slack.chatModel`/`chatEffort` (defaults sonnet/medium).
- **A requested write has exactly one destination** — the conversation is told that any file it writes goes in a per-thread scratch directory, `.ai-workspace/slack-scratch/<threadKey>/` (`getSlackScratchDir()` in `chat-scratch.ts`, folded into the first turn by `buildSlackChatPrompt`), and that everything else under the ai-workspace root — `workspace/`, `repositories/`, the rest of `.ai-workspace/` — is read-only. Together with the memory DB those are the only two writable paths.

  A prohibition alone was not enough, and the failure is specific: asked to review a PR, the conversation created `workspace/<name>.yml` as a place to keep the task. Nothing in the prompt covered it — hard limit (1) is scoped to the *git repositories / codebase*, and `workspace/` is neither — and the file was then unreachable from both ends: `listWorkspaces` / `listWorkspaceItems` skip every non-directory entry (`reader.ts`), there is no workspace-delete route (only `archive`), and hard limit (2) forbids the conversation from `rm`-ing anything. So the fix is an outlet plus a routing example rather than another "Do NOT" line (see **Prompt conventions**): the prompt now says outright that a file invented under `workspace/` does not create a workspace, and that a PR review / fix / new work request is answered by routing to the WebUI's Pull Requests tab or `init <description>`, never by setting something up.

  Nothing is created eagerly — `getSlackScratchDir` only computes the path (the prompt has the model `mkdir -p` on demand), since creating it per mention would leave an empty directory behind for every Slack question, which is the litter this exists to prevent. Per-thread rather than one shared directory so two threads asked for `notes.md` don't overwrite each other. The thread key is sanitized to a single path segment (separators and a dots-only key are rewritten), because it is interpolated into a prompt the model then uses as a path.
- **Session continuity** — CLI `session_id` keyed on `thread_ts ?? ts` (TTL 2 h, cap 200) persisted in `slack_conversation_sessions` (migration v8, `db/slack-sessions.ts`), so follow-ups `--resume` the same session and survive a restart. `RunClaudeOptions.resumeSessionId` seeds the spawn; `ClaudeProcess.getSessionId()` exposes the captured id (logged by `runClaude` on capture with a `claude --resume` hint). A resumed turn that fails with no output / non-zero exit (stale session) → `converse()` drops the id and retries **once** fresh.
- **Interim progress + hard cap** — a long turn is NOT killed at a short timeout. `runTurn` keeps the process alive and every `chatHeartbeatMs` (default 1 min) takes a snapshot of the assistant's accumulated text (`ClaudeProcess.getAssistantText()` — text blocks only, no tool noise) and compresses it to a one-line status via `summarizeProgress()` (`progress-summary.ts`, a throwaway `runClaude` call using `chatProgressModel`, default haiku, 30 s timeout). That summary is handed to `onProgress`; `handleConversation` renders it via `formatProgress()` ("⏳ {summary}", 300-char safety cap; bare "⏳ Still working…" when the snapshot is empty, summarization is disabled via `chatProgressModel: null`, or the summarizer failed) by editing the "🤔 Thinking…" placeholder in place (a `finished` guard stops a late edit clobbering the final answer; only one summary is in flight at a time). Only at `chatMaxTurnMs` (default 18 min) is the turn killed + reported as timed out — the `session_id` is persisted so replying in the thread resumes the work. The stale-session retry fires on `reason === "error"` only, never on the hard-cap timeout.
- **Per-user memory** (`slack.memoryEnabled`, default `true`) — each user gets a persistent memory in a **separate** SQLite file `.ai-workspace/slack-memory.sqlite` (`ensureSlackMemoryDb()` in `memory-db.ts`, NOT part of `db.sqlite` migrations) so a stray query can't touch operational data. No TS read/write path: the conversation Claude operates the DB itself via the `sqlite3` CLI, guided by instructions `buildSlackChatPrompt` folds into the first turn (DB path, `memories(id, user_id, content, …)` schema, the user's id, scoped SELECT/INSERT examples). Scoped strictly by `user_id`. `getSlackChatSystemPrompt()` grants read/write on the `memories` table (writes ONLY to `memories`, ONLY on explicit user request); keep it precise. `userId` flows `mention.user` → `handleConversation` → `converse(..., { userId })`; missing `userId` or disabled memory omits the block.
- **Thread folding** — the *first* conversation mention inside an existing thread (`mention.thread_ts` set, `hasThreadSession()` false) triggers `fetchThreadTranscript()` (`thread-fetch.ts`) via `conversations.replies` (paginated, cap 50×200), folded into the first-turn prompt (excluding the triggering mention; fetched before the placeholder). Resume turns skip it. Needs the channel-type history scope (`channels:history`/`groups:history`/`im:history`/`mpim:history`); on failure the conversation proceeds without thread context.

### Prompt conventions

Shared prompt fragments live in `src/lib/templates/prompts/shared.ts`. Compose system prompts from them rather than restating the wording per file — the working-directory rules in particular drifted per-agent before this existed. `src/__tests__/lib/templates/prompts/shared.test.ts` enforces adoption, including the invariant that no single prompt states both working-directory conventions.

- **Working directory** — `worktreeCdRules({ examples, forbidden?, extra? })` for single-worktree agents (executor, planner, reviewer, code-reviewer, verifiers, pr-creator): bare `cd` first, because the Bash sandbox blocks `cd <dir> && ...`. `NO_CD_RULES` for agents that span directories (collector, coordinator, researcher): never `cd`, always `-C` / path args. These two are mutually exclusive.
- **`WRITTEN_DELIVERABLE_LENGTH`** — length calibration for agents that write a file. Applied to every report writer because reports are re-embedded verbatim downstream (collector reads every review; the autonomous gate reads every review *and* every TODO file), so padding is paid for again in later phases. Also applied to the **planner**, whose TODO file is the most re-embedded deliverable of all: the executor re-reads it once per batch, the verifier audits it, and the gate reads every one each cycle. That is also why the planner's item format has three required fields (`Target` / `Action` / `Verify`) and two conditional ones (`Pattern` / `Why`, only where they change what the executor writes) rather than six mandatory ones — a uniform six-field shape both padded the file and cost the planner a search per item hunting for a `Pattern:` analogue it did not need. `Verify` doubles as the item's acceptance condition; there is no separate required `Acceptance` field.
- **The plan's item count is a cost, not a detail** — the planner's prompt has a `### What Is Not a TODO Item` section, and it exists because a plan for a two-file change came back with roughly forty items. Seven were "read this doc" (the TODO template's `## Initialize` prose expanded into a checklist) and six were the README's own constraint commands (lint / test / build / format / codegen / scope check), which the *old* prompt required: *"you MUST include corresponding verification TODO items"*. Those commands are already enforced twice without the planner's help — the executor runs the full declared set before marking anything `[x]`, and `Verify constraints` runs them again with a merge-base comparison — so the items bought a third copy and pushed the executor from one batch into three, at a measured 2–4 min per batch boundary. Item count is paid on every re-read: once per batch by the executor, once by the TODO verifier, and once per cycle by the gate. The prompt now sends the narrowest proving command into each item's `Verify:` field, allows **at most one** trailing whole-set item, and forbids itemizing documentation. `todo.ts`'s templates were the other half of the drift — they mandated a six-field shape including an `Acceptance:` field the planner prompt had already dropped, and shipped a `## Verification` section with one item per command; both are now aligned with the three-required-two-conditional rule above.

- **`REPO_SEARCH_EFFICIENCY`** — exploration strategy: locate code with `Grep`/`Glob`/`Read` rather than `grep`/`find`/`sed`/`cat` through Bash, and issue one step's independent lookups as **several tool calls in one turn**. Applied to the planner and the plan reviewer. It travels with `worktreeCdRules` because that rule is what suggests the `cd` idiom in the first place; it narrows `cd` to shell commands rather than forbidding it (forbidding it is `NO_CD_RULES`, a different convention for a different class of agent).

  **The first version of this fragment did not work, and the rewrite is aimed at four specific wording defects** — worth knowing, because each is a way a correct rule loses to the prompt around it. Re-measured on the phase it was written for: 54 Bash calls, **zero** `Grep`/`Glob`, and 73 assistant turns carrying **exactly one** tool call each.
  1. *"together in a single message" is harness vocabulary.* 26 of those 54 Bash calls packed several lookups into one command string with `;` and `echo ===` separators. The agent **did** batch — it just read "one message" as "one command", the one reading that saves nothing, since the shell round-trip is free and the model round-trip is the cost. The rule now names the unit, shows a four-call turn, and says outright that `;`-packing is not it.
  2. *A closed list is read as the closed list it is.* The old text named `grep` / `find` / `ls` / `cat`; the transcript used `sed` 9×, `awk` 2×, `wc` 2×, `head` 26× — none of them listed, so none of them felt covered. It is now a shell→tool table marked **non-exhaustive**, behind a statement of when a shell is needed at all.
  3. *`Read` looked inapplicable to the file that mattered.* Most `sed -n 'X,Yp'` calls were slicing a 17k-line generated `graphql.ts`. Nothing said `Read` takes `offset`/`limit`, so the shell was the only way to read a range. The table says so now.
  4. *It lost on emphasis and position.* It rendered immediately **before** `worktreeCdRules`, whose opening line is an all-caps MUST about a Bash call, and the planner's user prompt ends with a ` ```bash ` fence — so the last word on "how do I touch this repo" was Bash, twice. Rationale ("they are much faster than") does not outrank a MUST. The fragment now leads with the directive, renders **after** the cd rule (as it already did in `reviewer.ts`), and the planner's copy of the cd rule carries an `extra` pointing out of itself. The `### Execution Steps` — the part actually read as a procedure — name the tool at the point of use.

  The general lesson, and the reason this is documented rather than just fixed: a fragment competes with the prompt it is embedded in. Check what the operative steps say, what the *last* word on the subject is, and whether the instruction's unit is one the model can act on.
- **`SUBAGENT_DELEGATION_POLICY`** — when delegation is warranted, and that subagents must not be used to verify the agent's own output (later phases already verify). Applied to the agentic steps (executor, planner, code-reviewer, coordinator, researcher).
- **`SCOPE_DISCIPLINE`** — deliver the requested scope, neither narrowed nor widened; finish rather than leaving stubs. Applied to the executor and to the **TODO updater**, which is the other place a request's scope can grow: it is what turns a gate's numbered asks into the items an executor works from, and under `autonomous` the asks are *all* it receives (`buildCycleUpdateTodoPhase` passes `fixableIssues` as the `instruction` and nothing else — no `SUMMARY.md`, no review reports, no gate `reason`, no `dismissedFindings`), so it cannot check an ask against the reviewer's own wording.

  Its second paragraph exists because widening most often arrives looking like diligence: **imitating a neighbouring call site**. Asked for two SWR options on a new query, an updater cited the sibling hook that sets seven and prescribed all seven (correctly, by the repo's own convention — five other pre-existing sites carry that block verbatim); the executor landed them, and the five nobody asked for became the finding the run's final cycle spent its loop on, so it stopped with no PR. The rule is therefore that a cited pattern governs **form, not extent** — take its shape, change only the surface the request names — since the pattern is evidence of how the repository writes something, not that each part of it is right at this call site. The reviewer half of the same failure is the `new but not novel` rule in `SEVERITY_CALIBRATION`; neither half alone would have finished that run.

  The updater's own **`### Deriving an Item's Targets`** section (`updater.ts`) is the counterweight, and it renders immediately after `SCOPE_DISCIPLINE` because that rule is what suppressed both of its halves. Scope is about *how much* to change; this is about finding every place one change lands, where a missed site is not a narrower delivery but a wrong one. **Doc targets are enumerated by who states the contract**, not by which files the item already edits — the interface declaration, the implementation, and any comment documenting observable values — because the file with no code change of its own is both the one a caller reads and the one that derivation drops. It says outright that this is *not* widening, since a doc stating the contract being rewritten is the same change. **And test items must cover the sites the code items touch**: count them, and treat test files the request names as the floor rather than the ceiling, because the request was written from a review of the *old* code and cannot know which sites the items ended up changing. Measured on the run that produced both: a cycle whose items correctly added three doc sites the gate never named still missed the interface doc, and commissioned two test cases against five changed error-return sites — the three gaps were the next review's Warnings, and that review was the run's last, so it stopped with no PR. `update-todo` moved to `opus/high` in the same change (see **Model / effort resolution**) rather than instead of it: raising the rung on a wrong derivation rule only applies it more thoroughly.
- **`TOOLCHAIN_RESOLUTION`** / **`NO_TICKET_IDS_IN_CODE`** — extracted from `executor.ts` when a second code-writing agent (the since-removed `fix-applier`, see **Every cycle has one shape**) needed both verbatim. The executor is the only consumer today; they stay in `shared.ts` because the next code-writing agent must inherit the toolchain rule rather than re-derive it — "a command failing because the toolchain isn't set up is NOT a reason to give up", since an agent told to bail marks real work `[!]` blocked over an environment problem.
- **`REVIEW_COVERAGE_POLICY`** — the review→gate contract. Review agents report **everything**, including low-severity and uncertain findings, and annotate each with `(Confidence: high|medium|low)`; filtering is explicitly a downstream job. `collector.ts` preserves those annotations verbatim into `SUMMARY.md` (plus a Low-Confidence Findings count), and the autonomous gate's `### Confidence Filtering` section is where they turn into a decision: low-confidence findings alone never justify a loop, missing annotations count as medium, and confidence is independent of severity. Weakening any one of the three (report / carry / filter) silently changes the others' meaning: telling the reviewer to self-filter drops real bugs, and stripping confidence in the collector promotes speculation to fact.

  The policy also **withholds the ship/no-ship verdict** from the reviewer and the collector: neither may state that the branch can merge or ship, that it is "review-ready", or that findings are blocking / non-blocking. Enforced structurally as well as by prompt — `REVIEW_REPORT_TEMPLATE`'s `## Conclusion` and `SUMMARY_REPORT_TEMPLATE`'s carry that instruction in the placeholder, and the `| Overall Assessment | {assessment} |` row is gone from the summary's metrics table (a non-count that rendered an opinion as a counted fact). The reason is jurisdiction, not tone: a reviewer sees none of the acceptance criteria, TODO files, fix verification, or known-findings ledger the gate decides from, and `### Confidence Filtering` tells the gate the review "deliberately does not filter" — a claim a verdict falsifies. On the run this was written for, the review's Conclusion read *"none blocking. Merge-ready once the recommendations are triaged"* and `SUMMARY.md` reproduced it as `| Overall Assessment | Good — merge-ready … no blocking issues |`, while the gate — reading that same file and applying its own mapping — looped. Descriptive `## Overall Assessment` (Code Quality / Test Coverage / Security) stays; only the ruling is removed.

  Because `low` is the one label with a hard "never loops" rule attached, **what confidence measures** is stated at both ends and must stay in sync: it is whether the described **mechanism** is real, checked against the code — never how likely the triggering input is or how much the failure would matter. A finding that verified its mechanism and can only say the input is unconfirmed is `high`, with the unconfirmed exposure written into the finding body; the gate is told to read such a finding as high whatever label it arrived with, since only the *mechanism itself* being a guess is genuine low confidence. Conflating the two axes is how a verified regression dies: on the run this was written for, the reviewer established in code that `parseDate`'s 10-digit-exact `isUnixTimestamp` collapses a 13-digit millisecond timestamp to `0` — strictly worse than the `Number()` comparator the branch replaced — labelled it `low` because the backend's wire format was unconfirmed, and the gate correctly applied the low-confidence rule and dropped it. Note what actually decided that run: of three findings on the same field, only the one with a **concrete fix attached** looped (`### Decision Criteria` counts a Warning "with a concrete code change attached"), so in practice the reviewer's fix-attachment habit, not severity, chose what got fixed.
- **`SEVERITY_CALIBRATION`** — the other half of the loop bar. Since the autonomous gate loops only on Critical / Warning-level findings (see **Suggestion budget**), the severity label is what decides whether a finding is ever acted on, so it is anchored to one question about the change — *is it done, and is it sound?* — rather than to how cheap the fix looks or to what a later reader might prefer. Critical = broken; Warning = works but unfinished or unsound as delivered (unhandled failure path, contract not implemented, cross-boundary type mismatch, missing coverage for contract-required or reachable behavior); Suggestion = complete and correct, and this is taste — including an untested defensive guard no reachable input hits, which is the carve-out that keeps the coverage rule from having no fixed point (see **Suggestion budget**). One Warning class is scoped against the **diff rather than the repository**: an input class the code this change *replaced* handled and the new code does not. That is establishable from the diff alone, so not knowing how often the input arrives does not soften it — which is what makes it independent of the confidence axis above, where the same uncertainty had killed the finding. Bounded to the replaced code on purpose (a defect the change did not introduce is not its Warning), and the reviewer must attach the fallback change it would make if the open question is never answered, since a finding whose only exit is a human answer is one nothing acts on.

  The mirror of that bound is the **`new but not novel`** rule, which draws the same line around code the diff *does* contain. Before filing a Warning against a construct the change took from elsewhere in the repo — the same option block, helper or idiom — the reviewer must **search for other, pre-existing sites** of it; if they exist, the finding is about the repository's convention and is filed as a **Suggestion**, reported with the sites found (coverage untouched — it is filed lower, not dropped). Changing a convention from inside a feature branch means editing files the task never touched, and each is diff the review did not ask for. What keeps full severity is this change's *own* use being wrong here: the idiom does something different at this call site, or this is the one place the failure reaches a user. Without it, the reviewer's position is the only one in the pipeline where an established convention gets examined as if it were novel — the planner, gate, updater and executor all ground on repo precedent — so a defect in a five-site convention arrives as a blocking Warning on the newest code, which is exactly how one run spent cycle 3/3 on `dedupingInterval: Infinity` and stopped without a PR. The accepted cost: a genuinely broken convention the branch copied goes to the human on the PR rather than being fixed by a cycle. Applied to the code reviewer and cross-repo reviewer next to `REVIEW_COVERAGE_POLICY`: coverage says report everything, this says file it at the severity that matches its consequence, and confidence (not severity) is where uncertainty goes. A real defect filed under Suggestions is one the run will not come back to; a nit filed as a Warning costs a full cycle.
  **Untested paths get a three-rung table rather than prose**, because that is the class the label demonstrably drifts on across cycles: contract-required or asked for by an earlier cycle → Warning; reachable but neither → Suggestion; a defensive guard no reachable input hits → Suggestion. On the run this was written for, cycle 1 filed an untested transaction-failure path as a **Suggestion** *because* covering it needed a change to a shared mock the task did not own (the gate then ledgered it `deferred`, quoting that same cost back), while cycle 3 filed two untested error returns as **Warnings** on a diff a tenth the size — 118 changed lines against cycle 1's 1240. Same class, opposite labels, both derived from the price of the test rather than from the behavior. The drift tracks diff size (Warning density per 100 changed lines ran 0.16 → 1.3 → 4.2 across that run's three cycles), though size is confounded there: a contract threaded through three layers plus its doc comments is claim-dense in a way 1240 lines of new feature code is not.

  The middle rung is the one that did not exist before, and it is what keeps the coverage bullet from re-importing the unscoped rule the **Suggestion budget** rejects — without it every reachable branch of a fix diff is a Warning, which is the no-fixed-point bar arriving through coverage instead of through the guard carve-out. `explicitly asked for by an earlier cycle` is the other half: it stops a lost fix being downgraded to taste, the same precedence **Requested-fix verification** gives the verifier over the executor's checkboxes. The rungs grade *coverage of behavior believed correct* — a path that is itself wrong is a defect finding at its own severity, stated so the middle rung cannot become a way to file a broken error path as a preference.

  And the **cost of covering** a path is reported, never scored. That is jurisdiction, the same line `REVIEW_COVERAGE_POLICY` draws around the ship verdict: the gate holds the known-findings ledger and writes down why it declined, where the next cycle reads it. A reviewer that pre-declines by filing a Suggestion reaches the same conclusion with no record, and a Suggestion is not read again. Note what this does **not** buy: it would not have finished the run above, since both untested-return findings were behavior an earlier cycle had explicitly asked for and stay Warnings. What it buys is a label that reproduces when the same finding class arrives on a diff of a different size.
- **`RECURRING_FINDINGS_POLICY`** — the compression half of the same contract, and deliberately *not* a filter: a finding on the workspace's known-findings ledger is still reported, just as a single `(Recurring)` line outside the severity counts. Applied to the code reviewer and cross-repo reviewer, both of which also carry `REVIEW_COVERAGE_POLICY` — the two must travel together, since compression without coverage becomes suppression. See **Known-findings ledger** in Architecture for the write side. `knownFindingsSection()` renders the ledger into a user prompt under the one heading all three consumers (both reviewers, the gate) name.

Prompt wording follows Anthropic's Claude Opus 5 / Sonnet 5 prompting guides: prefer a positive example of the wanted behavior over a stack of "Do NOT" lines (see `getChatSystemPrompt()`'s first-turn spec), label example lists as non-exhaustive since Claude reads enumerations literally, and do not add "double-check your work" style instructions — the models self-correct, and the pipeline has explicit verification phases.

## Development Rules

- **TDD**: Write or update tests before implementing production code. First write a failing test, then implement.
- **Pre-commit checks**: Always run `bun run lint` and `bun run test` before committing. Both must pass with zero errors.
- **Git commands**: Run `git add`, `git commit`, and `git push` as separate commands — never chain them. Do not use `$()` substitution in git commands.

## Conventions

- Path alias: `@/*` → `./src/*`
- **`globalThis` pattern**: Mutable state (DB connection, pipeline operations, app config, chat sessions) stored on `globalThis` to survive Next.js HMR. Tests must account for this (see `test-setup.ts`).
- **`force-dynamic`**: All API routes export `const dynamic = "force-dynamic"`.

## Testing

Vitest with `@testing-library/react`, `@testing-library/jest-dom`. Globals enabled (no need to import `describe`/`it`/`expect`). `tsconfig.json` excludes test files — Vitest handles type-checking separately from `tsc --noEmit`.

**A DOM is granted by directory, not by extension** — `vitest.config.ts` declares two projects: `dom` (`environment: "jsdom"`, plus `src/test-setup-dom.ts` for the jest-dom matchers) covering `src/__tests__/components/**` and `src/__tests__/hooks/**`, and `node` covering everything else. A render test placed outside those two directories gets no `document` and fails on a name a `.tsx` extension would suggest it has; `hooks/` is matched as a directory for the mirror-image reason, since two of its render tests are `.ts`.

The split is there because `forks` + `isolate` (both Vitest defaults) give every test file its own process, so a jsdom built for the whole suite is built 159 times and shared by nothing: cumulative environment setup was **264s against a 22s wall clock**, more than every other phase of the run combined. Restricting it to the 24 files that render takes the suite from ~28s to ~14s. What it does *not* buy is a lower peak — that is set by the worker count times a worker, which is what root-level `maxWorkers: "60%"` addresses; the default of one worker per core bar one measured slower *and* larger, because the main vite process and the workers contend.

Neither knob is what makes a run eat the machine. That is an unbounded loop calling a `vi.fn()`, which retains every call's arguments in `mock.calls`: measured at ~275 bytes and ~2.75M calls per second, a spin reaches tens of GB in a couple of minutes and takes the machine into swap. `setup-repository.ts`'s branch-name search is bounded (`MAX_BRANCH_NAME_ATTEMPTS`) for that reason — a mock permissive enough to answer "yes, that branch exists" to every name is the ordinary way to write one. And **`pkill -f "vitest run <path>"` does not stop it**: a worker's command line is `vitest/dist/workers/forks.js` and carries no test path, so the pattern kills the parent and reparents the spinning worker to launchd, where it keeps growing. Kill the worker by pid.

## Gotchas

- **Config is cached on first access** — `getConfig()` stores on globalThis. Changes to `config.yml` require `_resetConfig()` to take effect. Tests must call reset functions in order: `_resetDb()` → `_resetConfig()` → `_resetWorkspaceRoot()`.
- **Event buffering is async** — Events aren't persisted immediately (500ms flush interval). Don't query events from the DB immediately after emitting them. SSE streaming replays from the in-memory buffer so clients see events before flush.
- **Workspace root must be set before config/DB** — The entire config directory and DB path depend on workspace root being known first. `bin/start.ts` calls `setWorkspaceRoot()` before `getConfig()`.
- **Function phase timeouts use separate AbortControllers** — Per-phase timeouts don't permanently abort the shared `managed.abortController` (which is for user-initiated kills). This is intentional to prevent timeout from killing the whole operation.
- **Running vs completed operations live in different stores** — Running operations are in-memory (`src/lib/pipeline/store.ts`). Completed ones are on disk. `/api/operations` merges both, with running taking precedence on dedup. The same route also serves `?status=completed&limit=N` (backed by `listRecentFinishedOperations`) for the "Recent Operations" panel on `/utilities/running`.
- **Constraint phases stop on first timeout** — In `review.ts`, constraint commands run sequentially and skip the rest after any timeout, since they're deterministic and later ones often depend on earlier artifacts. Stacking 5-min timeouts otherwise pushes the parent autonomous Cycle Review past its budget.
- **`runSubPhases` discards sub-phase `timeoutMs`** — it calls `runChild`/`runChildGroup`/`fn` directly, so the only budget that applies to a sub-pipeline run inside a function phase is the *wrapping* phase's. The `timeoutMs` values in `execute.ts` / `review.ts` / `update-todo.ts` therefore only take effect when those pipelines run as their own top-level operation; under `autonomous` they are inert. `CYCLE_BUDGETS_MS` in `autonomous.ts` is sized to cover each sub-pipeline end to end for that reason — except `execute`, whose budget depends on the configured `batchSize` and so is derived via `executeCycleBudgetMs()` (see `operations.batchSize` in Configuration). It also drops `phase.effort` (it forwards `model` but not `effort`), which is latent today because no sub-phase sets an explicit effort — they all resolve via `stepType`.
- **JSONL auto-migration** — On first startup, `getDb()` triggers `migrateJsonlToSqlite()` which imports legacy `.operations/` JSONL files if the SQLite table is empty.
- **Dev mode clears `.next` cache** — `bin/next-server.ts` removes `.next` on dev/hot startup to avoid stale route issues.
